## TL;DR

- BunがコアランタイムをZigからRustへ大規模移行。約100万行のコードが対象。
- AnthropicのClaude Codeがリライトを主導し、2000ファイル以上のPRを一括生成。
- 1Mトークンのコンテキスト窓を活用した「全域最適化」により、アーキテクチャの一貫性を維持。
- 技術的課題としてMiriチェックの失敗や `unsafe` の多用が指摘され、「Vibe Coding」論争が再燃。

## 背景：なぜBunはRustへ移行したのか

Bunはその誕生以来、Zigによる徹底的な低レイヤー最適化を武器に、Node.jsやDenoを凌駕するパフォーマンスを実現してきました。しかし、2026年5月、Bunチーム（現在はAnthropic傘下）はコア部分のRustへの移行という衝撃的な決定を下しました。

この移行の背景には、主に3つの要因があります。

1. **Rustエコシステムの成熟とメモリ安全性の保証**
2. **Zigコミュニティの「AI生成コードの投稿禁止」方針**
   AIファースト企業であるAnthropicにとって、AIによるコントリビューションを拒絶する言語での開発継続は困難でした。
3. **AIエージェントによる大規模リライトが可能になったこと**

## 技術的な詳細：100万行のAIリライト

今回のリライトは、人間による手作業ではなく、Anthropicの次世代エージェントツール「Claude Code」によって行われました。

### 1Mトークンコンテキストの威力

Claude Codeは100万トークンの巨大なコンテキスト窓を持ち、Bunの広大なcodebase全体を一度に「理解」することができました。これにより、ファイル単位の単純な変換ではなく、プロジェクト全体の依存関係やメモリアロケーションのパターンを維持したまま、Rustのイディオムへと再構成することが可能になりました。

- **対象ファイル数:** 2,188ファイル
- **行数:** 約94万行（コメント含む）
- **手法:** Zigの手動メモリ管理パターンをRustの `unsafe` ブロックやカスタムアロケータで一時的にラップしつつ、順次 Safe Rust へとリファクタリング。

### AIが生成したラッパーコードの例

AIによるリライトの過程で多用されたのが、Zigのアロケータセマンティクスを模倣する `unsafe` なラッパーです。

```rust
// AIが生成したZigのメモリアロケータパターンの模倣例
use std::alloc::{alloc, Layout};
use std::ptr;

pub struct ZigLikeAllocator {
    // 状態管理
}

impl ZigLikeAllocator {
    pub unsafe fn allocate<T>(&self, count: usize) -> *mut T {
        let layout = Layout::array::<T>(count).unwrap();
        let ptr = alloc(layout) as *mut T;
        if ptr.is_null() {
            std::alloc::handle_alloc_error(layout);
        }
        ptr
    }

    pub unsafe fn deallocate<T>(&self, ptr: *mut T, count: usize) {
        let layout = Layout::array::<T>(count).unwrap();
        std::alloc::dealloc(ptr as *mut u8, layout);
    }
}
```

こうしたコードは手動メモリ管理をそのまま引き継いでおり、Rustの借用チェッカー（Borrow Checker）の恩恵をフルには受けられません。AIは第一段階として「機能等価性」を重視した変換を行ったことがわかります。

## コミュニティの反応と「Vibe Coding」の懸念

この「AI主導の大規模移植」は、エンジニアコミュニティに激しい議論を巻き起こしています。

### 懸念点：コードの信頼性とMiriの失敗

Hacker Newsなどの議論では、移植されたRustコードが**Miri（Rustの未定義動作検出ツール）のチェックを多数通過できていない**ことが指摘されています。特に、Zigのセマンティクスを無理にRustで再現しようとした箇所で、以下のような未定義動作（UB）のリスクが残存しています。

```rust
// Miriでエラーとなる可能性のある強引なポインタ操作の例
unsafe {
    let mut data = vec![1, 2, 3];
    let ptr = data.as_mut_ptr();
    
    // AIが文脈を誤認し、エイリアス規則に違反する参照を生成
    let ref1 = &mut *ptr;
    let ref2 = &mut *ptr; // <- Data race & UB (Undefined Behavior)
    
    *ref1 = 10;
    *ref2 = 20;
}
```

借用チェッカーをバイパスする `unsafe` が多用されており、「見かけ上は動くが、Rust本来の安全性が失われている」という批判が相次いでいます。

### 「Vibe Coding」への論争

テストコードまでもがAIによって「通るように修正」されている可能性が指摘され、厳密なエンジニアリングではなく、AIの「雰囲気（Vibe）」でコードが書かれることへの恐怖が広がっています。一方で、ベンチマーク結果は以前と遜色ない、あるいは一部向上しているという報告もあり、実用性の観点からは成功しているという声も無視できません。

## 考察：実運用視点での「AIによる基盤リライト」

今回のBunの事例は、システムプログラミングにおける「人間の役割」が劇的に変化していることを示唆しています。

100万行規模のインフラコードを、数日で別の言語に移植する——。これは従来、数年単位のプロジェクトであり、多くの場合は失敗に終わるものでした。それがAIによって数日で（不完全ながらも）達成されたという事実は、今後のインフラ開発が「一から書く」ものから「AIが生成したものを人間が監査・修正する」ものへとシフトすることを決定づけました。

筆者（Kaoru）としては、この「AI生成インフラ」をどう安全に運用するかが、これからのSREやプラットフォームエンジニアの核心的なスキルになると考えています。具体的には、**「AIが出力した unsafe コードの静的解析と自動修正パイプラインの構築」** や **「Miri をCIプロセスに組み込み、未定義動作を徹底的に弾く仕組み」** など、人間によるレビューを補完する堅牢なテストインフラが不可欠になります。

## まとめ

BunのRust移行は、単なるプログラミング言語の変更ではなく、**「AIが基盤ソフトウェアを自ら書き換える」**時代の幕開けを告げる象徴的な出来事です。コードの安全性やメンテナビリティに関する課題は山積みですが、この巨大な実験がJavaScriptランタイム、ひいてはソフトウェア開発全般にどのような影響を与えるか、引き続き注視が必要です。
