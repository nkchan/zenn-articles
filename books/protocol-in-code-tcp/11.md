## この章の問い

前章の teardown は4パケットと待ち時間を使って、丁寧に会話を畳みました。では、RST 1つで終わる接続は、その4パケットと待ち時間の**何を省略しているのか**。そして、RSTなら何でも接続を終わらせられるわけではないとしたら、**何がその正当性を決めているのか**。

この章を読み終えると、次のことが言えるようになります。

- `ResetDisposition` の3つの結果を挙げ、RSTフラグが立っていないセグメントにはどれが対応するかを言える
- RSTのシーケンス番号が「ウィンドウ内」であるとはどういうことか、そしてなぜそれをチェックするのかを説明できる
- 3つの結果それぞれで `state` に何が起きるかを言える
- RSTが接続に与える影響を、`teardown.py` の4パケット・忍耐強い経路と対比できる

対応するソースファイルは `src/protocol_in_code/tcp/reset.py` です。

## RSTは会話ではなく、打ち切りである

第9章の teardown は「両者が合意して閉じる」プロトコルでした。FINを送り、相手のACKを待ち、相手のFINを待ち、TIME_WAITでさらに待つ。4つのセグメントと、`TWO_MSL` 秒の沈黙が必要でした。

RSTはこの手続きを一切踏みません。読む型そのものがそれを物語っています。

```python
class ResetDisposition(str, Enum):
    ACCEPTED = "Accepted"
    IGNORED = "Ignored"
    NOT_A_RESET = "NotAReset"


@dataclass(frozen=True)
class ResetOutcome:
    """RST ends everything now, with no goodbye - the opposite of teardown.py's patient four packets."""

    disposition: ResetDisposition
    new_state: str
    note: str
```

`ResetDisposition` は3つしかありません。`teardown.py` の `CloseState` が8つの状態（`ESTABLISHED`, `FIN_WAIT_1`, `FIN_WAIT_2`, `CLOSING`, `TIME_WAIT`, `CLOSE_WAIT`, `LAST_ACK`, `CLOSED`）を持ち、その間を段階的に遷移していたのとは対照的です。RSTの世界に段階はありません。**受け入れられるか、無視されるか、そもそもリセットではないか**の3つだけです。

`new_state` の型に注目してください。`CloseState` のようなenumのメンバーではなく、ただの `str` です。これは第1章で見た `Segment` の設計判断（`flags` は集合であってビットマスクではない）とは違う理由の、もう一つの意図的な選択です。`reset.py` は `teardown.py` を一度もインポートしていません。RSTで閉じることと、FINで閉じることは、**同じenumを共有しない、別々の終わり方**として書かれています。両者を結びつけるのは、この章の外にいる `speaker.py`（第11章）の仕事です。

## `on_reset()` ―― 正当性は1つの窓で決まる

この章の本体です。

```python
def on_reset(state: str, segment: Segment, rcv_nxt: int, window: int) -> ResetOutcome:
    """An in-window RST slams any state straight to CLOSED; an out-of-window RST is just noise."""
    if not is_rst(segment):
        return ResetOutcome(ResetDisposition.NOT_A_RESET, state, "not a reset, nothing to do")

    if in_receive_window(segment.seq, rcv_nxt, max(window, 1)):
        return ResetOutcome(
            ResetDisposition.ACCEPTED,
            CLOSED_STATE,
            "in-window RST: connection is aborted immediately, no reply, no wait",
        )

    # RFC 5961 challenge-ACK behavior is out of scope here; we simply note the drop.
    return ResetOutcome(
        ResetDisposition.IGNORED,
        state,
        "out-of-window RST: ignored (a real stack would send a challenge ACK)",
    )
```

判定は2段階です。

```text
segment に RST フラグが無い                          -> NOT_A_RESET, state はそのまま
segment に RST があり、seq が [rcv_nxt, rcv_nxt+window) 内 -> ACCEPTED, state -> "Closed"、返信なし
segment に RST があり、seq がその窓の外                -> IGNORED, state はそのまま
```

### 第一関門 ―― `is_rst(segment)`

最初のチェックが `is_rst(segment)` であることには理由があります。これを最初に置くことで、それ以降の全ての分岐は「このセグメントは確かにRSTである」という前提の上で書けます。チェックすべきフラグは1つだけで、「ここでやることは何もない」を弾き出せる。第1章で見た `validate_segment()` の判定順（先に形式、後で意味）と同じ設計の型です。

### 正当性判定 ―― ウィンドウ内かどうか

`is_rst()` を通っても、それだけでは接続は閉じません。**そのRSTのシーケンス番号が、受信側の現在のウィンドウの内側にあるか**が、正当性の唯一の基準です。

```python
in_receive_window(segment.seq, rcv_nxt, max(window, 1))
```

`in_receive_window()` は `seqnum.py` の関数で、`reassembly.py` や受信経路の他の場所でも使われている、同じウィンドウ算術です。`on_reset()` はシーケンス番号の比較を自分で再実装していません ―― 既にある関数を再利用しています。

```python
def in_receive_window(seq: int, rcv_nxt: int, window: int) -> bool:
    """A seq is acceptable if it falls in [rcv_nxt, rcv_nxt + window), wrap included."""
    if window <= 0:
        return seq == rcv_nxt
    offset = (seq - rcv_nxt) % SEQ_SPACE
    return offset < window
```

なぜこのチェックが必要なのでしょうか。RSTは、正当な通信相手からの終了要求だけでなく、経路上の攻撃者が偽装したセグメントである可能性もあります。もし「RSTフラグさえ立っていれば無条件に接続を閉じる」という実装なら、シーケンス番号を推測または観測できた第三者が、任意の接続を落とせてしまいます。ウィンドウ内チェックは、そのRSTが「今この接続が期待しているデータの範囲」に触れているかどうかを確かめる、最低限の正当性の担保です。

`max(window, 1)` にも意味があります。呼び出し側が誤って `window=0` を渡しても、`in_receive_window()` にはウィンドウ幅1として渡されます。`in_receive_window()` 自身も `window <= 0` のとき `seq == rcv_nxt` に倒れますが、`on_reset()` はその手前で `max(window, 1)` によって「ウィンドウ0だから全てのRSTを拒否する」という状況を避けています。

### ACCEPTED ―― 返信なし、待ちなし

```python
CLOSED_STATE = "Closed"
```

ウィンドウ内のRSTが受け入れられると、`state` は即座に `"Closed"` になります。返信のセグメントはありません。`ResetOutcome` の3番目のフィールドである `reply` は ―― そもそもこのモジュールには存在しません。`teardown.py` の `TeardownStep` が `reply: Segment | None` を持っていたのとは対照的です。RSTには「相手に返す挨拶」がない。届いた時点で、話は終わっています。

### IGNORED ―― 静かに無視される

ウィンドウの外から来たRSTは、`IGNORED` として捨てられます。`state` は変わりません。ソースのコメントが率直にそのおもちゃの境界を明かしています。

```python
# RFC 5961 challenge-ACK behavior is out of scope here; we simply note the drop.
```

RFC 5961は、ウィンドウ内だが未検証のRSTに対して「チャレンジACK」を送り返し、相手が本物のシーケンス番号でRSTを再送してくるかを確かめる仕組みを定義しています。このおもちゃはその応答を実装していません。ウィンドウの外にあるRSTは単にノイズとして扱われ、何も送り返されません。

## 自分で答える問い

ソースファイルを見て答えてください（docstring ではなく関数の本体で）。

1. `on_reset()` は `rcv_nxt` と `window` をプレーンな整数として受け取ります。`ReceiveBuffer` のようなオブジェクトではありません。呼び出し側は、この関数を呼ぶ前に何を計算しておく必要があり、それは `speaker.py` のどこで行われているか。
2. なぜ `on_reset()` はシーケンス番号を見るより先に `is_rst(segment)` をチェックするのか。逆の順序ではなぜいけないのか。
3. `ACCEPTED` 分岐での `new_state` の型は何か。`state` がもともと `CloseState` のメンバーだった場合、`IGNORED` 分岐の `new_state` とはどう違うか。
4. `window` が `0` として渡されたとき、`in_receive_window()` が実際に見るウィンドウ幅はいくつか。`on_reset()` のどの行がそれを決めているか。
5. `CloseState.FIN_WAIT_1` から受け入れられたRSTと、`teardown.py` の4パケット経路を全部踏んだFINは、どちらも最終的に「もう交渉することが何もない」接続にたどり着きます。`on_reset()` の `ACCEPTED` 分岐と、`teardown.py` の `time_wait_expired()` の役割を読み比べると、RSTの経路が**決して生み出さないもの**は何か。

（問い2の答えの入口: `is_rst(segment)` が偽なら、シーケンス番号を見る意味自体がない ―― `NOT_A_RESET` はセグメントの中身に関する判断ではなく、「そもそもこの関数が扱う対象か」という手前の判断だから。）

## 動かして確認する

```bash
PYTHONPATH=src python3 examples/tcp/session_10_walkthrough.py
```

walkthrough は、`ESTABLISHED` な接続にウィンドウ内のRSTを送って即座にクローズすること、同じRSTのシーケンス番号だけをウィンドウの外にずらすと `IGNORED` になり状態が変わらないこと、RSTフラグの無いセグメントは `NOT_A_RESET` になること、`FIN_WAIT_1` の途中でもRSTは同じように効くこと、そして `teardown.py` のFIN経路と比べてRSTがどれだけ早く終わるかを確かめます。実行結果はこうなります。

```text
Session 10 walkthrough: RST ends everything now

[OK] in-window RST on ESTABLISHED -> Accepted new_state=Closed
[OK] out-of-window RST ignored     -> Ignored new_state=Established
[OK] non-RST segment                -> NotAReset new_state=Established
[OK] in-window RST during FIN_WAIT_1 -> Accepted new_state=Closed
[OK] RST vs FIN: RST already Closed -> FIN path only reached FinWait1
```

最後の行が、この章の核心を1行にまとめています。`initiate_close()` を呼んでFINを送った側は、まだ `FIN_WAIT_1` に着いたばかり ―― CLOSEDまでは残り3パケットと待ち時間があります。同じ瞬間、同じ接続にRSTが1本届けば、その接続は既に `"Closed"` です。`[OK]` は、この非対称性が予想通りにコードへ現れていることを意味します。

## この章を終えたと言える条件

ノートを見ずに、次を全部言えれば合格です。

- 「RSTが接続を閉じられるのは、そのシーケンス番号が受信側の現在のウィンドウ内にあるときだけ ―― それ以外はただのノイズ」
- 「RSTには返信も待ちもない。ACCEPTEDは一直線にクローズへ向かい、TIME_WAITに相当するものはこの経路のどこにもない」
- 「`on_reset()` と `teardown.py` はenumを共有していない ―― `reset.py` の `new_state` はただの文字列で、この2つを1つの `state` に統合するのは `speaker.py` だけの仕事」

ここまでで、TCPが会話を終える2つの方法を読みました。第9章の忍耐強い4パケットと、この章の即断即決の1パケットです。どちらも `state` を最終的に閉じた状態へ導きますが、経路も、正当性の基準も、残すものも全く違いました。

次章 ―― 最終章 ―― では、ここまで11本のファイルに分けて読んできた部品が、`speaker.py` という1つのオブジェクトに配線されます。ハンドシェイク、データ配送、輻輳、そしてこの章のリセットとteardown。エンドポイント1つの一生を、部品の寄せ集めではなく1つの流れとして眺めたとき、何が見えるのか ―― それが最後の問いです。
