## この章の問い

TCPのコネクションを閉じるのに、なぜ片方が話し終えた瞬間ではなく、4つのセグメントと、そのあとの**待ち時間**が要るのか。

この章を読み終えると、次のことが言えるようになります。

- `CloseState` の8つの値を挙げ、それぞれをアクティブ側（先に閉じる側）とパッシブ側（後から閉じる側）のどちらが訪れるかを言える
- アクティブ側を `FIN_WAIT_1` → `FIN_WAIT_2` → `TIME_WAIT` と辿り、ワイヤ上のセグメントがちょうど4つであることを数えられる
- パッシブ側を `CLOSE_WAIT` → `LAST_ACK` → `CLOSED` と辿れる
- `TIME_WAIT` が「セグメントが届いたら終わる状態」ではなく「時間そのものを待つ区間」であることを説明できる

対応するソースファイルは `src/protocol_in_code/tcp/teardown.py` です。

## これまでの章との境界線

第2章で読んだハンドシェイクは、コネクションを開く側が2つの役割（アクティブ・パッシブ）に分かれ、それぞれ別の3状態の経路を辿り、`ESTABLISHED` だけで合流する、という構造でした。この章のteardownは、その**閉じる版**です。ただし対称性は同じではありません。ハンドシェイクは3セグメントで終わりましたが、close は4セグメントに加えて、セグメントが1つも届かない**待ち時間**が要ります。

理由は単純です。TCPは全二重です。片方が「もう送るデータがない」と言うことと、もう片方が同じことを言うことは、**別々の独立した出来事**です。だから、それぞれの方向を独立に閉じる必要がある ―― これが「半クローズ (half-close)」という考え方の土台になります。

## 状態は8つ、片側4つずつ

```python
class CloseState(str, Enum):
    ESTABLISHED = "Established"
    FIN_WAIT_1 = "FinWait1"
    FIN_WAIT_2 = "FinWait2"
    CLOSING = "Closing"
    TIME_WAIT = "TimeWait"
    CLOSE_WAIT = "CloseWait"
    LAST_ACK = "LastAck"
    CLOSED = "Closed"
```

8つのうち `ESTABLISHED` と `CLOSED` は開始点・終着点として両側が共有しますが、途中の6状態は綺麗に2グループに分かれます。

| グループ | 状態 | 訪れるのは |
|---|---|---|
| アクティブ側の経路 | `FIN_WAIT_1`, `FIN_WAIT_2`, `CLOSING`, `TIME_WAIT` | 先に `close()` を呼んだ側 |
| パッシブ側の経路 | `CLOSE_WAIT`, `LAST_ACK` | 相手のFINを先に受け取った側 |

`CLOSING` は例外的な状態で、双方がほぼ同時に閉じようとした「同時クローズ」でだけ現れます。通常の片側主導のcloseでは、アクティブ側は `FIN_WAIT_1 -> FIN_WAIT_2 -> TIME_WAIT` を辿り、`CLOSING` は経由しません。

大事なのは、ハンドシェイクのときと同じく、**アクティブ側とパッシブ側は同じ状態遷移図を辿っていない**ということです。両者が合流するのはそれぞれ別の終着点（アクティブ側は `TIME_WAIT` を経て `CLOSED` に、パッシブ側は `LAST_ACK` を経て `CLOSED` に）で、遷移の途中に共有される状態はありません。

## 遷移の結果を運ぶ `TeardownStep`

```python
@dataclass(frozen=True)
class TeardownStep:
    new_state: CloseState
    reply: Segment | None
    note: str
    wait_started_at: int | None = None
```

第2章の `HandshakeStep` に、フィールドが1つ増えています。

| フィールド | 意味 |
|---|---|
| `new_state` | このセグメント（または `close()` 呼び出し）を処理した後、どこに着地するか |
| `reply` | 送り返すセグメント。ローカルの状態だけが変わるステップなら `None` |
| `note` | 何が起きたかを一行で説明する ―― このトラックを通して使われている習慣 |
| `wait_started_at` | `TIME_WAIT` に**入った瞬間だけ**セットされる。待ち時間に関するすべての計算は、このタイムスタンプ1つから導かれる |

`wait_started_at` がこの章の主役です。ここに刻まれる「時刻」だけが、あとで待ちが終わったかどうかを判定する唯一の材料になります。

## アクティブ側の主戦場 `on_segment_active()`

```python
def initiate_close(seq: int) -> tuple[CloseState, Segment]:
    """The active closer speaks first too: send FIN, and start waiting for the other three."""
    fin = Segment(seq=seq, ack=0, flags=frozenset({"FIN"}))
    return CloseState.FIN_WAIT_1, fin


def on_segment_active(state: CloseState, segment: Segment, now: int) -> TeardownStep:
    """Goodbye takes four packets (and a wait): the active side tracks its own FIN and the peer's."""
    if state is CloseState.FIN_WAIT_1:
        if is_fin(segment) and is_ack(segment):
            ack = Segment(seq=segment.ack, ack=segment.seq + 1, flags=frozenset({"ACK"}))
            return TeardownStep(CloseState.TIME_WAIT, ack, "peer FIN+ACK, closing now", now)
        if is_ack(segment):
            return TeardownStep(CloseState.FIN_WAIT_2, None, "our FIN acked, waiting for peer's FIN")
        if is_fin(segment):
            # Simultaneous close: both sides sent FIN before hearing the other's ACK.
            ack = Segment(seq=segment.ack, ack=segment.seq + 1, flags=frozenset({"ACK"}))
            return TeardownStep(CloseState.CLOSING, ack, "simultaneous FIN, acked peer's")
        return TeardownStep(state, None, "waiting for ACK of our FIN")

    if state is CloseState.FIN_WAIT_2:
        if is_fin(segment):
            ack = Segment(seq=segment.ack, ack=segment.seq + 1, flags=frozenset({"ACK"}))
            return TeardownStep(CloseState.TIME_WAIT, ack, "peer FIN arrived, entering time-wait", now)
        return TeardownStep(state, None, "waiting for peer's FIN")

    if state is CloseState.CLOSING:
        if is_ack(segment):
            return TeardownStep(CloseState.TIME_WAIT, None, "peer acked our FIN, entering time-wait", now)
        return TeardownStep(state, None, "waiting for ack of our FIN")

    return TeardownStep(state, None, "nothing left to negotiate")
```

`initiate_close()` は `active_open()` の兄弟です。自分の `seq` を載せた素のFINを組み立て、`FIN_WAIT_1` に移って待つ。それだけです。

### `FIN_WAIT_1` 分岐 ―― 3通りを見分ける

ここが最も枝分かれの多い箇所です。アクティブ側は`FIN_WAIT_1`で、次の4パターンのどれが届くか分かりません。

```text
peer FIN+ACK が同時に届いた -> TIME_WAIT （相手はFINとACKを1つのセグメントに乗せてきた）
peer ACK のみ届いた         -> FIN_WAIT_2 （自分のFINは確認された。相手のFINはまだ）
peer FIN のみ届いた         -> CLOSING    （同時クローズ。相手のACKをまだ聞いていない）
どちらも届いていない        -> FIN_WAIT_1 のまま、まだ待つ
```

「自分のFINが確認されたか」と「相手のFINが届いたか」は、**独立した2つの事実**です。この分岐はまさにその独立性をコードにしたものです。両方が同時に真になる（FIN+ACK）、片方だけが真になる（ACKのみ、あるいはFINのみ）、どちらも真でない ―― 4通りの組み合わせのうち、意味を持つ3通りに対応する枝が用意されています。

`CLOSING` に進む枝には注目してください。相手のFINは届いたが、自分が送ったFINへのACKはまだ来ていない。この状態は「双方が相手のACKを聞く前に同時にFINを送った」ケースにだけ現れます。

### `FIN_WAIT_2` 分岐 ―― 残りの1つを待つだけ

自分のFINは既にackされているので、あとは相手のFINを待つだけです。届けばACKを返して `TIME_WAIT` へ。

### `CLOSING` 分岐 ―― 最後のピースを待つ

相手のFINには既にACKを返してあるので、あとは自分のFINに対するACKを待つだけです。届けば、返信を送らずに `TIME_WAIT` へ。

3つの分岐すべてが、最終的に `TIME_WAIT` に着地するとき `wait_started_at=now` をセットしていることに注目してください。**`TIME_WAIT` に入る経路は3通りあっても、そこに刻まれる時刻の意味は1つだけ**です ―― 「ここから先、時間だけを見る」という合図です。

## パッシブ側 ―― セグメントでは動かない状態がある

```python
def on_segment_passive(state: CloseState, segment: Segment) -> TeardownStep:
    """The passive closer hears FIN first, and lingers in CLOSE_WAIT until its own app is done."""
    if state is CloseState.ESTABLISHED:
        if is_fin(segment):
            ack = Segment(seq=segment.ack, ack=segment.seq + 1, flags=frozenset({"ACK"}))
            return TeardownStep(CloseState.CLOSE_WAIT, ack, "peer FIN arrived, acked it")
        return TeardownStep(state, None, "connection is open, nothing to close")

    if state is CloseState.CLOSE_WAIT:
        # The passive side's own close() call, not a segment, is what fires this - modeled
        # in the speaker capstone. Here we only describe the wire step: send our own FIN.
        return TeardownStep(state, None, "waiting for local application to call close()")

    if state is CloseState.LAST_ACK:
        if is_ack(segment):
            return TeardownStep(CloseState.CLOSED, None, "peer acked our FIN, fully closed")
        return TeardownStep(state, None, "waiting for ack of our FIN")

    return TeardownStep(state, None, "nothing left to negotiate")


def passive_close(seq: int) -> tuple[CloseState, Segment]:
    """CLOSE_WAIT's own application finally calls close(): send our FIN, await the last ACK."""
    fin = Segment(seq=seq, ack=0, flags=frozenset({"FIN"}))
    return CloseState.LAST_ACK, fin
```

### 半クローズが可視化される場所

`CLOSE_WAIT` の分岐が、この章でいちばん立ち止まる価値がある箇所です。相手のFINは既に届いてACK済みなのに、この分岐は**どんなセグメントを渡されても `state` を変えません**。コメントがその理由をそのまま書いています ―― ここから先に進めるのはセグメントの到着ではなく、**ローカルのアプリケーションが `close()` を呼ぶこと**だけです。

これが半クローズです。相手は「もう送らない」と言った（FIN）。しかしこちら側はまだデータを送りたいかもしれない。TCPはその判断をプロトコルの外、アプリケーションに委ねます。`on_segment_passive()` の `CLOSE_WAIT` 分岐が何もしないのは怠慢ではなく、**ここでTCPが判断すべきことが何もない**からです。

このおもちゃモデルでは `CLOSE_WAIT` 中にペイロードを送る経路自体がありません（後述）が、構造として「相手の意思」と「自分の意思」が別々のトリガーで扱われている点はここで確認できます。

`passive_close()` は、そのローカルの `close()` 呼び出しをモデル化した関数です。`initiate_close()` と全く同じ形でFINを組み立て、`LAST_ACK` に移って最後のACKを待ちます。

### `LAST_ACK` 分岐 ―― 単純な最後の一段

```text
ACKが届いた -> CLOSED、送るものなし
それ以外    -> LAST_ACK のまま、まだ待つ
```

ここまで来れば、あとは自分のFINへのACKを待つだけの単純な分岐です。

## `time_wait_expired()` ―― 「期限つきの値」がここにも現れる

```python
def time_wait_expired(entered_at: int, now: int) -> bool:
    """TIME_WAIT is patient on purpose: it must outlast any stray segment still crossing the network."""
    return now - entered_at >= TWO_MSL
```

1行です。`TIME_WAIT` について、モジュールが読むのはこの比較だけです。第5章で読んだ再送タイマーは、「セグメントを送った時刻」を覚えておき、`now` との差が `RTO` を超えたら再送する、という形をしていました。`TIME_WAIT` はまったく同じ形をしています ―― `wait_started_at`（≒ `entered_at`）という**時刻を持った値**を覚えておき、`now` との差が `TWO_MSL` という閾値を超えたら状態が切り替わる。

この本を貫くテーマの一つ、「期限つきの値」がここにも現れています。再送タイマーは「時間内に確認が来なければ動く」形でしたが、`TIME_WAIT` は逆に「時間内は動かず、時間が来たら動く」形です。どちらも、**値そのものではなく、値と現在時刻の差**が判断材料になっている点は同じです。

`TWO_MSL` はモジュール冒頭のただの定数 `240` です。

```python
TWO_MSL = 240
```

秒だとはどこにも書かれていません。実物のTCPではMSL（Maximum Segment Lifetime）の2倍という具体的な意味を持ちますが、このおもちゃでは「比較対象になる目盛りの数」でしかありません。`time_wait_expired()` を純粋な比較関数にできているのは、まさにこの抽象化のおかげです。

## なぜ `TIME_WAIT` は「セグメントを待つ」のではないのか

ここがこの章のいちばんの読みどころです。`on_segment_active()` を最後まで見てください ―― `TIME_WAIT` を処理する分岐はどこにもありません。`FIN_WAIT_1`、`FIN_WAIT_2`、`CLOSING` は扱いますが、`TIME_WAIT` になった後にセグメントが届いても、この関数は関与しません。

`TIME_WAIT` から抜けるための唯一の経路は `time_wait_expired()` で、これは `Segment` を一切引数に取りません。**セグメントの到着ではなく、時間の経過だけ**が `TIME_WAIT` を終わらせます。

なぜそんな遠回りが必要なのか。最後のACK（アクティブ側が送った、相手のFINへの確認）が届かなかったら、相手は `LAST_ACK` のまま止まり、いずれFINを再送してきます。もしアクティブ側がACKを送った直後に `CLOSED` になっていたら、その再送FINに応答するコネクションはもう存在しません。`TIME_WAIT` は、そうした「まだネットワーク上をさまよっているかもしれない古いセグメント」が届ききるまで、コネクションの記録をあえて残しておく待機時間です。

## Decision Flow

```text
アクティブ側 (initiate_close してから on_segment_active):
  ESTABLISHED  --initiate_close()-->        FIN_WAIT_1
  FIN_WAIT_1   --peer FIN+ACK-->            TIME_WAIT   (返信: ACK)
  FIN_WAIT_1   --peer ACK のみ-->           FIN_WAIT_2
  FIN_WAIT_1   --peer FIN（ACKまだ）-->     CLOSING     (返信: ACK、同時クローズ)
  FIN_WAIT_2   --peer FIN-->                TIME_WAIT   (返信: ACK)
  CLOSING      --peer ACK-->                TIME_WAIT
  TIME_WAIT    --now - entered_at >= TWO_MSL-->  CLOSED (time_wait_expired()、セグメント不要)

パッシブ側 (on_segment_passive してから passive_close):
  ESTABLISHED  --peer FIN-->                CLOSE_WAIT  (返信: ACK)
  CLOSE_WAIT   --ローカルの close()-->      LAST_ACK    (返信: FIN、passive_close() 経由)
  LAST_ACK     --peer ACK-->                CLOSED
```

## Reading Lens ―― この章で問い直すべきこと

「コネクションを閉じる」を1つのイベントとして見るのをやめ、セグメントごとに次を問い直してください。

- どちら側が最初にFINを送ったか ―― 自分は今アクティブ経路を読んでいるのか、パッシブ経路を読んでいるのか
- 相手のFINが届いたかどうかとは無関係に、**自分自身のFINは既にackされているか**
- このステップが `TIME_WAIT` に着地するなら、`wait_started_at` は何だったか、`now` はそこからどれだけ離れているか

## おもちゃの境界

このモジュールは、実際のセグメントに駆動される1本のコネクションの完全なcloseをモデル化しています。ただし、ACKが返ってこないFINを**再送**する仕組みはありません。実物のスタックならタイムアウトして `initiate_close()` のFINを再送しますが、ここでは `on_segment_active()` は単に `FIN_WAIT_1` に留まり、もう一度待つだけです。

同時クローズは限定的な形で存在します。`on_segment_active()` は `FIN_WAIT_1` で相手のACKより先にFINが届くケースを `CLOSING` への遷移として扱いますが、鏡写しのケース ―― パッシブ側から見た同時クローズ ―― のテストはありません。`on_segment_passive()` は、自分がFIN前の状態にいる間に相手のFINを観測することがそもそもないからです（最初の分岐は `ESTABLISHED` にキーされています）。

半クローズ（FINを受け取った後もアプリケーションがデータを送り続けるケース）はモデル化されていません ―― パッシブ側の `CLOSE_WAIT` 分岐は、ペイロードを一切検査しません。

そして `TWO_MSL` は秒数ではなく、抽象的な目盛りの整数です。walkthroughはこれを純粋に「`now` と比較するための閾値」として扱います。


walkthroughは、1本のコネクションを4セグメントの能動的closeで最後まで駆動し（FIN、相手FINへのACK、相手の最後のFINへのACK、相手側のFIN）、ワイヤを渡ったセグメントがちょうど4つであることを数え、パッシブ側を `CLOSE_WAIT` から `LAST_ACK` を経て `CLOSED` まで駆動し、`time_wait_expired()` が `TWO_MSL` の境界で `False` から `True` へ切り替わることを確認します。出力はこうなります。

```text
Session 09 walkthrough: Goodbye takes four packets (and a wait)

[OK] client initiate_close        -> state=FinWait1 seq=1000
[OK] client hears ACK of our FIN  -> state=FinWait2
[OK] client hears peer's FIN      -> state=TimeWait wait_started_at=10
[OK] server hears client's FIN    -> state=CloseWait
[OK] server app calls close()     -> state=LastAck seq=5000
[OK] server hears last ACK        -> state=Closed
[OK] exactly four segments sent   -> count=4
[OK] one tick before TWO_MSL      -> expired=False
[OK] exactly at TWO_MSL           -> expired=True
```

各行の `[OK]` は、「そのステップが予想通りの状態・予想通りのフィールド値になった」という意味です。3行目に注目してください。クライアントが相手のFINを聞いて `TimeWait` に着地したとき、`wait_started_at=10` が実際にセットされています ―― これがこの後の `time_wait_expired()` の計算の起点そのものです。最後の2行は、`entered_at=10` から `TWO_MSL` 手前の1目盛りではまだ `False`、ちょうど `TWO_MSL` に達した瞬間に `True` へ切り替わることを、実際の比較で確かめています。境界値そのものを跨いだ結果が `True` になる点は、自分で答える問い1の答え合わせにもなっています。

## この章を終えたと言える条件

ノートを見ずに、次を全部言えれば合格です。

- 「closeが4セグメント要るのは、各側の**自分のFIN**と**自分のACK**が、それぞれ独立した出来事だから」
- 「`TIME_WAIT` はセグメントを待っているのではない。`entered_at + TWO_MSL` に対する時間の計算を待っている」
- 「`CLOSE_WAIT` が先に進むのは、常にローカルのアプリケーションが `close()` を呼んだときだけで、セグメントが届いたからではない」

次章では、この4パケットと待ち時間の手続きを、まるごと**すっ飛ばして**終わらせる仕組みを読みます。RSTは、正規の手順が保証していたことのどこを省略しているのか。そして、そもそも「コネクションを即座に終わらせてよい」という判断を、RSTに許しているのは何なのか ―― `reset.py` を開きます。
