## この章の問い

コネクションを確立するのに、なぜセグメントがちょうど3つ要るのか。そして、それぞれのセグメントを受け取る**前**、双方はどんな状態にいて、受け取った**後**にどう変わるのか。

この章を読み終えると、次のことが言えるようになります。

- `ConnectionState` の5つの状態を挙げ、どれが一時的でどれが起点かを言える
- クライアント側の経路 `CLOSED -> SYN_SENT -> ESTABLISHED` を追える
- サーバ側の経路 `LISTEN -> SYN_RCVD -> ESTABLISHED` を追える
- 最後のACKが、なぜ返信セグメントを一切生まないのかを説明できる

対応するソースファイルは `src/protocol_in_code/tcp/handshake.py` です。

## 第1章との境界線

第1章で読んだ `validate_segment()` は、一度も `ConnectionState` を見ませんでした。SYNとFINが同時に立っているのが間違いなのは、接続がどの状態にあろうと常に間違いだからです。それは**セグメント単体の正しさ**でした。

この章で読むのはその続きです。セグメント単体としては正しくても、「今この状態でこのセグメントを受け取っていいか」は別の問いになります。`LISTEN` 状態でSYN+ACKを受け取ることに意味はないし、`ESTABLISHED` に達した後にSYNが届いても、もう交渉することは何もありません。これが**状態に依存する正しさ**です。ハンドシェイクは、この2種類の正しさの境界線を最初にまたぐ場所です。

## 状態は5つ、そのうち2つは通過点

```python
class ConnectionState(str, Enum):
    CLOSED = "Closed"
    LISTEN = "Listen"
    SYN_SENT = "SynSent"
    SYN_RCVD = "SynRcvd"
    ESTABLISHED = "Established"
```

`CLOSED` と `LISTEN` は、それぞれの側が出発点として持つ状態です。クライアントは `CLOSED` から動き出し、サーバは `LISTEN` で待ち構える。`SYN_SENT` と `SYN_RCVD` は**一時的な状態**で、次に期待するセグメントが届くまでの間しか存在しません。そして `ESTABLISHED` が、ハンドシェイクという仕事の終着点です。

大事なのは、クライアントとサーバが**同じ状態遷移図を辿っていない**ということです。クライアントは `CLOSED -> SYN_SENT -> ESTABLISHED` という3状態の経路を、サーバは `LISTEN -> SYN_RCVD -> ESTABLISHED` という別の3状態の経路を辿ります。両者が合流するのは、最後の `ESTABLISHED` だけです。

## 遷移の結果を運ぶ `HandshakeStep`

```python
@dataclass(frozen=True)
class HandshakeStep:
    new_state: ConnectionState
    reply: Segment | None
    note: str
```

3つのフィールドだけです。

| フィールド | 意味 |
|---|---|
| `new_state` | このセグメントを処理した後、接続がどこに着地するか。入力の状態と同じこともよくある |
| `reply` | 送り返すセグメント。何も送る必要がなければ `None`。サーバ側では、最後のACKを処理した結果が `reply=None` になる ―― ハンドシェイクはそこで単に終わる |
| `note` | この遷移が起きた理由を説明する一行。プロトコルのデータではなく、walkthrough（そしてあなた）がトレースを言葉にできるように存在するだけ |

`note` がプロトコルデータではないという注記は読み飛ばさないでください。ワイヤに乗るのは `new_state` と `reply` だけで、`note` は人間向けの注釈です。第1章の `flags_label()` が「表示のための順序」を後から与えていたのと同じで、説明はデータそのものとは別の場所にあります。

## クライアントの最初の一手 `active_open()`

```python
def active_open(iss: int) -> tuple[ConnectionState, Segment]:
    """The client speaks first: send SYN, and wait."""
    syn = Segment(seq=iss, ack=0, flags=frozenset({"SYN"}))
    return ConnectionState.SYN_SENT, syn
```

クライアントにできることは1つだけです。自分の `iss`（initial sequence number）を `seq` に載せた素のSYNを組み立て、`SYN_SENT` に移り、待つ。`ack` はまだ意味を持ちません ―― クライアントはまだサーバから何も聞いていないからです。

## `on_segment()` ―― 状態ごとに枝分かれする本体

この章の本命が `on_segment()` です。状態を受け取り、セグメントを受け取り、`HandshakeStep` を返します。

```python
def on_segment(state: ConnectionState, segment: Segment, iss: int) -> HandshakeStep:
    """It takes three packets to say hello: SYN, SYN+ACK, ACK - each a state transition."""

    # --- passive-open path: a listener hears a SYN and answers with its own ---
    if state is ConnectionState.LISTEN:
        if is_syn(segment):
            syn_ack = Segment(
                seq=iss,
                ack=segment.seq + 1,
                flags=frozenset({"SYN", "ACK"}),
            )
            return HandshakeStep(ConnectionState.SYN_RCVD, syn_ack, "heard SYN, sent SYN+ACK")
        return HandshakeStep(state, None, "listening, nothing to do yet")

    if state is ConnectionState.SYN_RCVD:
        if is_ack(segment) and not is_syn(segment):
            return HandshakeStep(ConnectionState.ESTABLISHED, None, "heard final ACK, established")
        return HandshakeStep(state, None, "still waiting for the final ACK")

    # --- active-open path: the initiator hears SYN+ACK and closes the loop ---
    if state is ConnectionState.SYN_SENT:
        if is_syn(segment) and is_ack(segment):
            final_ack = Segment(
                seq=segment.ack,
                ack=segment.seq + 1,
                flags=frozenset({"ACK"}),
            )
            return HandshakeStep(ConnectionState.ESTABLISHED, final_ack, "heard SYN+ACK, sent final ACK")
        if is_syn(segment):
            # Simultaneous open: both sides opened at once. Not this course's focus.
            return HandshakeStep(state, None, "heard bare SYN while syn-sent, ignoring")
        return HandshakeStep(state, None, "waiting for SYN+ACK")

    if state is ConnectionState.ESTABLISHED:
        return HandshakeStep(state, None, "already established, handshake is over")

    return HandshakeStep(state, None, "closed, nothing to negotiate")
```

### `LISTEN` 分岐 ―― `ack` の意味がここで初めて具体化する

リスナーは、SYNを聞くまで何もしません。聞いたら、返信の `ack` は `segment.seq + 1` になります。これはこのコードベースで最初に出てくる「`ack` とは『次に期待するバイト』であって『今受け取ったバイト』ではない」という具体的な証拠です。SYNは1バイト分のシーケンス空間を消費する制御セグメントなので、「次に期待する」は「受け取った `seq` + 1」になります。

### `SYN_RCVD` 分岐 ―― ACKだけを待つ

```text
ACKが立っていてSYNが立っていない -> ESTABLISHED, 何も送らない
それ以外                          -> SYN_RCVD のまま、まだ待つ
```

サーバは、SYN+ACKを送った後、純粋なACK（SYNを伴わない）が返ってくるのを待つだけです。

### `SYN_SENT` 分岐 ―― 「SYN+ACK」と「SYNのみ」を区別する

ここが読みどころです。「SYNとACKが両方立っている」（`ESTABLISHED` に進み、最後のACKを返信する）場合と、「SYNのみ」（同時オープンとして明示的に無視する）場合の違いをよく見てください。最後のACKの `seq` は `segment.ack` です ―― クライアントは、サーバが「次に期待する」と教えてきた値を、そのまま送り返します。これは `ack` の意味が「次に期待するバイト」であることを裏側から確かめる形になっています。

### `ESTABLISHED` とフォールスルー

いったん `ESTABLISHED` に達すると、以降どんなセグメントが来ても `on_segment()` は状態を変えず、何も送りません。フォールスルーの `CLOSED` も同様で、交渉することは何もありません。

## Decision Flow

```text
state = LISTEN,     segment に SYN あり            -> SYN_RCVD, SYN+ACK を送る
state = LISTEN,     segment に SYN なし            -> LISTEN のまま, 送るものなし

state = SYN_RCVD,   segment に ACK あり・SYN なし  -> ESTABLISHED, 送るものなし
state = SYN_RCVD,   それ以外                       -> SYN_RCVD のまま, まだ待つ

state = SYN_SENT,   segment に SYN と ACK が両方   -> ESTABLISHED, 最後のACKを送る
state = SYN_SENT,   segment に SYN のみ            -> SYN_SENT のまま, 無視（同時オープン）
state = SYN_SENT,   それ以外                       -> SYN_SENT のまま, まだ待つ

state = ESTABLISHED                                -> ESTABLISHED, 交渉することは何もない
state = CLOSED（フォールスルー）                   -> 変化なし, 交渉することは何もない
```

## この章で座って考える価値がある一点

3つ目のセグメント ―― クライアントからサーバへの最後のACK ―― が、この章で一番考える価値がある箇所です。これはサーバを `ESTABLISHED` に進めますが、`HandshakeStep.reply` は `None` です。ハンドシェイクの完了は、それ自体としてはワイヤ上のトラフィックを何も生まない**状態変化**です。

ハンドシェイクを「SYN、SYN-ACK、ACKという3つの互換可能なステップ」として眺めるのをやめて、セグメントごとに次のように問い直すことが、この章の核心的な読み方です。

- このセグメントが届く**前**、この側はどの状態にいたか
- 返信の `seq` と `ack` は、何が確認された（acknowledge された）ことを語っているか
- この遷移は、送信すべきセグメントを生んだのか、それとも内部的な状態変化だけだったのか

## おもちゃの境界

実物のTCPは、SYNとSYN+ACKセグメントの中でMSS、ウィンドウスケーリング、SACK許可といったオプションを交渉し、初期シーケンス番号はスプーフィング対策のランダム性を持って選ばれます ―― 単純な `iss` 引数として渡されるわけではありません。このおもちゃは `iss` をパラメータとして受け取ることで、walkthroughのどのシナリオも再現可能にしています。時計もランダム性もありません。

`on_segment()` は同時オープン（`SYN_SENT` が素のSYNを受け取るケース）を明示的に認識していますが、コメントは「このコースの焦点ではない」と言い切っています。RFC 9293にある4セグメントの同時オープン・ハンドシェイクへのコードパスは、ここには存在しません。

再送、タイムアウト、SYNが失われた場合の `SYN_SENT` の再試行ロジックは、完全にスコープ外です。このセッションのどのシナリオも、セグメントは順序通りに、一度だけ届くことを前提にしています。

## 自分で答える問い

ソースファイルを見て答えてください（docstring ではなく関数の本体で）。

1. `SYN_RCVD` にいるサーバが、SYNとACKが両方立ったセグメントを受け取った。どの分岐がこれを処理し、サーバはどの状態に落ち着くか。
2. `final_ack.ack` は、SYN+ACKセグメントのどのフィールドの式で表せるか。`SYN_SENT` 分岐を読んで、正確な式を導け。
3. `SYN_SENT` にいるクライアントが、素のSYN（ACKなし）を受け取ったら、`on_segment()` は何を返すか。`note` フィールドは、その理由をどう説明しているか。
4. 接続が `ESTABLISHED` に達した後、それ以降どんなセグメントが来ても、`on_segment()` は何を返すか。フラグの内容に関わらず、か。
5. `state=CLOSED` のとき、任意のセグメントに対して `on_segment()` をトレースせよ。どの分岐が処理し、`new_state` は何か。

（問い1の答えの入口: `SYN_RCVD` 分岐は `is_ack(segment) and not is_syn(segment)` を見ている。SYNとACKが両方立っているセグメントはこの条件を満たさない ―― `is_syn(segment)` が真だから `not is_syn(segment)` が偽になる。だから最初の `if` は外れ、`else` の "still waiting for the final ACK" に落ち、状態は `SYN_RCVD` のまま変わらない。）

## 動かして確認する

```bash
PYTHONPATH=src python3 examples/tcp/session_02_walkthrough.py
```

walkthroughは、ハンドシェイクの両側を実際に駆動します。クライアントの `active_open()` から始め、サーバとクライアントの `on_segment()` を交互に呼び、ワイヤに実際に乗ったセグメントの数を数え、両側がちょうど3つのセグメントの後に `ESTABLISHED` に着地することを確かめます。出力はこうなります。

```text
Session 02 walkthrough: It takes three packets to say hello

[OK] client active_open          -> state=SynSent seq=1000
[OK] server hears SYN            -> state=SynRcvd seq=5000 ack=1001
[OK] client hears SYN+ACK        -> state=Established seq=1001 ack=5001
[OK] server hears final ACK      -> state=Established reply=None
[OK] both sides established      -> client=Established server=Established
[OK] exactly three segments sent -> count=3
[OK] handshake ignored once done -> already established, handshake is over
```

各行の `[OK]` は、「その手順が予想通りの状態・予想通りのフィールド値になった」という意味です。特に3行目と4行目に注目してください。クライアントは `seq=1001 ack=5001` で `ESTABLISHED` に進み、サーバは最後のACKを受け取って `reply=None` のまま `ESTABLISHED` に進みます ―― 送るものが何もないまま状態だけが変わる、という節で説明した通りの挙動が、ここで実際に確認できます。最後の行は、ハンドシェイクが終わった後に届いた（遅れて再送された）SYNが単に無視されることも示しています。

## この章を終えたと言える条件

ノートを見ずに、次を全部言えれば合格です。

- 「クライアントとサーバはそれぞれ別の3状態の経路を持ち、両者が合流するのは最後の `ESTABLISHED` だけ」
- 「ハンドシェイクはちょうど3つのセグメントで終わる ―― SYN、SYN+ACK、ACK。3つ目は自分自身の返信を生まない」
- 「どのセグメントの `ack` も常に『次に期待するバイト』であり、相手の `seq` に1を足して計算される」

次章では、この `seq` という数字がいつまでも増え続けるわけではないことを読みます。32bitの空間は一周し、0に戻る。そのとき「before」とは何を意味するのか ―― `seqnum.py` を開きます。
