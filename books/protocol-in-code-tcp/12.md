## この章の問い

ハンドシェイク、シーケンス番号、ウィンドウ、再送タイマー、高速再送、輻輳制御、順序の乱れの吸収、teardown、RST ―― これまで10章かけて別々に読んできた部品を、1つのオブジェクトに配線したら何が起きるのか。

この章を読み終えると、次のことが言えるようになります。

- `ToyTcpEndpoint` の全フィールドを挙げ、それぞれがどの章の部品かを言える
- `state` が接続の一生の中で**2種類の異なるenum型**を保持する理由と、それがバグではなく意図的な継ぎ目であることを説明できる
- `on_segment()` のディスパッチ順序を追え、なぜ `on_reset()` が状態別の分岐より**先に**、無条件で走るのかを言える
- 2つのエンドポイントをハンドシェイクからデータ転送、能動的closeを経て `CLOSED` まで走らせ、`trace` を正としてその過程を読める

対応するソースファイルは `src/protocol_in_code/tcp/speaker.py` です。

## この章が読み方を切り替える

これまでの10章は、1章に1つのソースファイル、1つの疑問でした。「セグメントとは何か」「なぜ3パケットか」「シーケンス番号はどう一周するか」―― それぞれのファイルは、他のファイルをほぼ意識せずに読めました。

`speaker.py` は違います。新しいアルゴリズムは1行もありません。中身は全部、第1章から第10章までで読んだ関数と型の**呼び出し**です。この章で読むべきものは「新しい判断」ではなく、「**誰がいつ呼ばれるか**」という配線そのものです。読み方も変わります ―― 1行ごとに「これは第何章の部品か」を確認しながら読むのが、この章の正しい読み方です。

## `ToyTcpEndpoint` ―― 全フィールドは前の章からの借り物

```python
@dataclass
class ToyTcpEndpoint:
    """Build the toy TCP loop: one endpoint's state, wired to every session in this track."""

    name: str
    iss: int
    state: object = ConnectionState.CLOSED
    clock: int = 0
    rcv_nxt: int = 0
    recv_buffer: ReceiveBuffer = field(default_factory=lambda: ReceiveBuffer(capacity=4096))
    reassembly: ReassemblyBuffer | None = None
    estimator: RttEstimator = field(default_factory=RttEstimator)
    congestion: CongestionState = field(default_factory=CongestionState)
    ack_tracker: AckTracker = field(default_factory=AckTracker)
    time_wait_entered_at: int | None = None
    trace: list[str] = field(default_factory=list)
```

このクラスの新規性は「フィールドがあること」ではなく「**全部集まっていること**」です。対応関係を表にすると、この章がやっていることの全体が見えます。

| フィールド／インポート | 出典の章 | `ToyTcpEndpoint` での役割 |
|---|---|---|
| `Segment`, `is_fin`, `is_rst`, `flags_label` | 第1章 | すべての関数が読み書きするワイヤ単位 |
| `ConnectionState`, `active_open`, `on_segment` | 第2章 | `state` の1つ目のenum空間。`active_open()` とESTABLISHED前の `on_segment()` を駆動 |
| シーケンス演算（`window.py` 経由・`reset.py` 内部） | 第3章 | 受信ウィンドウとRSTのウィンドウチェックの土台にあるリング演算 |
| `ReceiveBuffer`, `advertised_window` | 第4章 | `recv_buffer`。その `advertised_window()` は `on_reset()` のウィンドウチェックに直結 |
| `RttEstimator` | 第5章 | `estimator` ―― 全エンドポイントが持つが、この章のwalkthroughは `observe()` を一度も呼ばない |
| `AckTracker`, `on_ack`（`track_ack`としてインポート）, `AckSignal` | 第6章 | `ack_tracker`。`_on_data()` がデータセグメントのたびに呼び、重複ACKを監視 |
| `CongestionState`, `on_ack`, `on_timeout` | 第7章 | `congestion`。`track_ack()` の返り値に応じて `_on_data()` が `cwnd` を伸ばすかリセットする |
| `ReassemblyBuffer`, `deliver` | 第8章 | `reassembly`。ハンドシェイクが `ESTABLISHED` に達した瞬間に生成され、以降のデータセグメントは全部 `deliver()` を通る |
| `ResetDisposition`, `on_reset` | 第10章 | `on_segment()` の一番最初のチェック。状態別分岐より前に走る（後述） |
| `CloseState`, `initiate_close`, `on_segment_active`, `on_segment_passive`, `passive_close` | 第9章 | `state` の2つ目のenum空間。`close()` とESTABLISHED後の `on_segment()` を駆動 |

この表で第10章（`reset.py`）が第9章（`teardown.py`）より先に並んでいるのは、`on_segment()` が実際にそう**呼ぶ順序**だからで、章の並び自体が入れ替わったわけではありません。教材としては第9章「teardown」を先に学び、第10章「RST」を後で学びますが、実行時には RST チェックの方が先に走ります。この「学ぶ順序」と「実行される順序」のズレそのものが、この章で押さえておきたい観察の1つです。

## `state` が2つのenum空間を持つ理由

クラス定義の直前にあるコメントが、この章で最初に読むべき一文です。

```python
# CloseState.ESTABLISHED and ConnectionState.ESTABLISHED are two enums that mean the same
# thing at two different moments in one connection's life; the endpoint below tracks both
# spaces in a single `state` field by storing whichever enum member currently applies.
```

`state: object = ConnectionState.CLOSED` ―― 型注釈があえて `object` です。`ConnectionState | CloseState` という union にもできたはずですが、そうしていません。理由は、`ConnectionState.ESTABLISHED` と `CloseState.ESTABLISHED` が**同じ接続上の瞬間**を指す、しかし**別々のenumのメンバー**だからです。

なぜ1つのenumに統合しなかったのか。第2章の `handshake.py` と第9章の `teardown.py` を、互いに知らなくていいファイルとして独立させておくためです。`handshake.py` は `CloseState` の存在を知らなくていいし、`teardown.py` は `ConnectionState` の存在を知らなくていい。その独立性の代償として、両方を橋渡しする役目が `ToyTcpEndpoint` 1箇所に集中します。これはバグではなく、意図して置かれた継ぎ目です。だからこそ `state` の型は緩く `object` にしてあり、`isinstance(self.state, ConnectionState)` と `isinstance(self.state, CloseState)` という実行時チェックで、今どちらの空間にいるかを判定します。

## `on_segment()` ―― このトラック全体のディスパッチ表

```python
def on_segment(self, segment: Segment) -> Segment | None:
    """Dispatch by current state and flags - handshake, reset, teardown, then data."""
    reset_outcome = on_reset(self.state, segment, self.rcv_nxt, advertised_window(self.recv_buffer))
    if reset_outcome.disposition is ResetDisposition.ACCEPTED:
        self.state = CloseState.CLOSED
        self.trace.append(f"{self.name}: {reset_outcome.note}")
        return None

    if isinstance(self.state, ConnectionState) and self.state is not ConnectionState.ESTABLISHED:
        step = handshake_on_segment(self.state, segment, self.iss)
        self.state = step.new_state
        self.trace.append(f"{self.name}: {step.note} -> {step.new_state.value}")
        if step.new_state is ConnectionState.ESTABLISHED:
            self.rcv_nxt = segment.seq + (1 if segment.payload_len == 0 else segment.payload_len)
            self.reassembly = ReassemblyBuffer(rcv_nxt=self.rcv_nxt)
        return step.reply

    if isinstance(self.state, CloseState):
        return self._on_segment_teardown(segment)

    # ESTABLISHED and carrying data or a peer-initiated FIN.
    if is_fin(segment):
        step = on_segment_passive(CloseState.ESTABLISHED, segment)
        self.state = step.new_state
        self.trace.append(f"{self.name}: {step.note} -> {step.new_state.value}")
        return step.reply

    return self._on_data(segment)
```

読む順に、5段階です。

```text
on_segment(segment):
  1. on_reset(state, segment, rcv_nxt, advertised_window(recv_buffer))
       ACCEPTED  -> state = CloseState.CLOSED, trace に記録, return None（無条件でここで止まる）
       それ以外  -> 通過。state はまだ触れられていない
  2. state が ConnectionState かつまだ ESTABLISHED でない
       -> handshake.on_segment() へディスパッチ。ESTABLISHED に達したら
          最終セグメントから rcv_nxt を確定し、reassembly を生成
  3. state が CloseState
       -> _on_segment_teardown():
            CLOSE_WAIT               -> 何もしない（close() だけがこの状態を進める）
            LAST_ACK                 -> on_segment_passive()
            FIN_WAIT_1/2 または CLOSING -> on_segment_active()
  4. state が ConnectionState.ESTABLISHED かつセグメントに FIN が立っている
       -> on_segment_passive(CloseState.ESTABLISHED, segment): CLOSE_WAIT へ
  5. それ以外（ESTABLISHED、データセグメント）
       -> _on_data(): reassembly に deliver()、続いて track_ack() し
          congestion.on_ack() か congestion.on_timeout() に反映
```

### なぜ `on_reset()` が最初に、無条件で走るのか

`on_segment()` の最初の一文が `on_reset(...)` です。`self.state` がハンドシェイク中なのか、確立済みなのか、close手続きの途中なのかを**一度も確認する前に**、RSTかどうかのチェックが走ります。

これは、`on_reset()` のシグネチャが `rcv_nxt` と `window` という**プレーンな引数**を受け取るだけで、接続状態を意識した関数ではないからです。RSTは接続がどの段階にあっても同じ規則でチェックされる ―― ハンドシェイクの途中に届いたRSTも、確立後に届いたRSTも、close手続きの最中に届いたRSTも、`on_reset()` にとっては同じ入力です。「RSTだけは状態機械の外側にある例外的な扱いを受ける」という事実が、この1行の並び順に表れています。

### `_on_data()` ―― 第6章と第7章の連携

```python
def _on_data(self, segment: Segment) -> None:
    if segment.payload_len <= 0 or self.reassembly is None:
        return None
    result = deliver(self.reassembly, segment.seq, segment.payload_len)
    self.rcv_nxt = result.new_rcv_nxt
    self.trace.append(f"{self.name}: data seq={segment.seq} -> {result.outcome.value}, rcv_nxt={self.rcv_nxt}")
    signal = track_ack(self.ack_tracker, segment.ack)
    if signal is AckSignal.FAST_RETRANSMIT:
        congestion_on_timeout(self.congestion)
        self.trace.append(f"{self.name}: {AckSignal.FAST_RETRANSMIT.value}, cwnd={self.congestion.cwnd}")
    elif signal is AckSignal.NEW_DATA_ACKED:
        congestion_on_ack(self.congestion)
    return None
```

ここで第8章（`reassembly.deliver()`）と第6章（`fast_retransmit.track_ack()`）と第7章（`congestion.on_ack()` / `on_timeout()`）が1つの関数の中で順番に呼ばれます。まずデータを届け（`deliver()`）、その結果とは独立に、届いたセグメントのACK値から重複ACKの兆候を調べ（`track_ack()`）、その兆候の種類によって輻輳ウィンドウを操作する（`congestion_on_ack()` または `congestion_on_timeout()`）。3つの章が3つの別々の判断として存在していたものが、ここでは1本のシーケンスになります。

`AckSignal` は3値のはずですが、ここで分岐しているのは `FAST_RETRANSMIT` と `NEW_DATA_ACKED` の2つだけです。残るもう1つの値（重複だが3回目未満のACK）は、どちらの分岐にも当たらず `cwnd` に触れません。これは本文を読むと確認できる、この章の「自分で答える問い」の1つです。

### `_on_segment_teardown()` ―― LAST_ACKだけが特別扱いされる理由

```python
def _on_segment_teardown(self, segment: Segment) -> Segment | None:
    if self.state is CloseState.CLOSE_WAIT:
        return None  # only close() drives this state forward, not an incoming segment

    # LAST_ACK belongs to the passive closer's path; every other close state here
    # (FIN_WAIT_1, FIN_WAIT_2, CLOSING) belongs to the active closer's path.
    if self.state is CloseState.LAST_ACK:
        step = on_segment_passive(self.state, segment)
    else:
        step = on_segment_active(self.state, segment, self.clock)

    self.state = step.new_state
    self.trace.append(f"{self.name}: {step.note} -> {step.new_state.value}")
    if step.new_state is CloseState.TIME_WAIT:
        self.time_wait_entered_at = step.wait_started_at
    return step.reply
```

第9章で `teardown.py` は `on_segment_active()` と `on_segment_passive()` という2つの独立した関数として書かれていました。ここで両者を橋渡ししているのが、コード中のコメントそのものです ―― 「`LAST_ACK` は受動的にcloseする側の経路に属し、それ以外（`FIN_WAIT_1`、`FIN_WAIT_2`、`CLOSING`）は能動的にcloseする側の経路に属する」。この `if` 1つが、`teardown.py` の2つの関数を1つのディスパッチにまとめる、この章全体の橋そのものです。

`TIME_WAIT` に入った瞬間だけ `time_wait_entered_at` を記録している点にも注目してください。この値を消費するのは、この関数ではなく `tick()` です。

### `tick()` ―― セグメントではなく時計だけがTIME_WAITを終わらせる

```python
def tick(self, seconds: int) -> None:
    self.clock += seconds
    if self.state is CloseState.TIME_WAIT and self.time_wait_entered_at is not None:
        from .teardown import time_wait_expired

        if time_wait_expired(self.time_wait_entered_at, self.clock):
            self.state = CloseState.CLOSED
            self.trace.append(f"{self.name}: time-wait expired at clock={self.clock}, closed")
```

`speaker.py` の中で `time_wait_expired()` を呼んでいるのはここだけです。`on_segment()` がどれだけセグメントを処理しても、`TIME_WAIT` から `CLOSED` へは進みません。進めるのは時計を進めることだけです。第9章で読んだ「期限つきの値」というテーマが、ここで最終的な形で現れています。

### `close()` ―― 1つのメソッド、状態で分かれる2つの振る舞い

```python
def close(self) -> Segment:
    """Either close the connection actively (send FIN first) or answer a pending FIN."""
    if self.state is CloseState.CLOSE_WAIT:
        self.state, fin = passive_close(self.iss)
        self.trace.append(f"{self.name}: application close(), sent {flags_label(fin)}")
        return fin

    self.state, fin = initiate_close(self.iss)
    self.trace.append(f"{self.name}: application close(), sent {flags_label(fin)}")
    return fin
```

`self.state` が `CLOSE_WAIT` かどうかだけで、`passive_close()` と `initiate_close()` のどちらに進むかが決まります。どちらもFINを組み立てる点は同じで、違うのは結果として作られる `CloseState` だけです。「アプリケーション側からの `close()` 呼び出し」という1つの操作が、接続がどちら側からcloseされたかによって別の状態遷移になる ―― この分岐が、能動的closeと受動的closeという2つの経路の入口です。

## `run_three_way_handshake()` ―― 最小の統合デモ

```python
def run_three_way_handshake(client: ToyTcpEndpoint, server: ToyTcpEndpoint) -> None:
    """The smallest integration demo: two endpoints trade three segments and both reach ESTABLISHED."""
    server.listen()

    syn = client.active_open()
    syn_ack = server.on_segment(syn)
    assert syn_ack is not None
    final_ack = client.on_segment(syn_ack)
    assert final_ack is not None
    reply = server.on_segment(final_ack)
    assert reply is None
```

第2章で読んだ「3パケットのハンドシェイク」が、ここでは2つの `ToyTcpEndpoint` オブジェクトの間で実際に交換されます。ただし、この関数がやるのはハンドシェイクだけです。データ転送、RST、teardownは一切駆動しません ―― それらを一続きに見せるのは、次の「動かして確認する」で実行するwalkthroughの役目です。

## おもちゃの境界

`MSS = 1` ―― このモジュール自身のテストとwalkthroughに登場するデータセグメントは、すべて1バイトです。これは第8章の `reassembly.py` のシーケンス演算を読みやすく保つための単純化であって、実際のセグメント化を再現するものではありません。

`state: object = ConnectionState.CLOSED` の型注釈があえて緩いことは前述の通りです。`ConnectionState.ESTABLISHED` と `CloseState.ESTABLISHED` という同じ瞬間を指す2つのenumメンバーを1つのフィールドで扱う ―― これは埋めるべきバグではなく、教えるべき設計上の継ぎ目として、意図的に残されています。

`estimator`（`RttEstimator`、第5章）は全エンドポイントに存在しますが、`on_segment()` からも `tick()` からも `observe()` は一度も呼ばれません。つまりこのモジュールには再送タイマーの配線がありません。再送タイマーの実物を動かすのは第5章のwalkthroughの役目であって、この章の統合対象には含まれていません。

受動的closeは `close()` メソッドの `CLOSE_WAIT` 分岐からしか到達できず、テストかwalkthroughが明示的に呼ばない限り、`on_segment()` が自動的にそこへ導くことはありません。そして `run_three_way_handshake()` は、その名の通りハンドシェイクだけを実演します ―― データにもRSTにもteardownにも触れません。

## 自分で答える問い

ソースファイルを見て答えてください（docstring ではなく関数の本体で）。

1. `on_segment()` は、`self.state` が `ConnectionState` か `CloseState` かを確認する**前に** `on_reset()` を呼びます。もし接続がまだ `SYN_SENT`（データを一度も受け取っていない）の段階でRSTが届いたら、そのRSTはどんな `rcv_nxt` の値と照合されるか。
2. `_on_segment_teardown()` で、なぜ `LAST_ACK` だけが独自の `if` 分岐を必要とし、`FIN_WAIT_1` / `FIN_WAIT_2` / `CLOSING` と同じ `on_segment_active()` 呼び出しに合流できないのか。
3. `on_segment()` が `self.rcv_nxt` を設定し `self.reassembly` を生成するのは、`ConnectionState.ESTABLISHED` に達する分岐の中だけです。もしデータセグメントが1回早く、`self.reassembly` がまだ `None` のときに届いたら何が起きるか。
4. `tick()` は `self.state is CloseState.TIME_WAIT` を確認してから `time_wait_expired()` を呼びます。それ以外の状態のとき、`self.time_wait_entered_at` はどうなるか ―― `tick()` がそれをクリアすることはあるか。
5. `_on_data()` は全てのデータセグメントで `track_ack()` を呼び、返ってきた `AckSignal` を見ます。3つある `AckSignal` の値のうち、`congestion` の `cwnd` を一切変化させないのはどれか。

（問い1の答えの入口: `self.rcv_nxt` はデフォルト値 `0` のまま初期化されており、`SYN_SENT` の段階ではまだ誰からも更新されていない。つまりこのRSTは「まだ何も受け取っていない」という前提の `rcv_nxt=0` と照合される。）

## 動かして確認する

```bash
PYTHONPATH=src python3 examples/tcp/session_11_walkthrough.py
```

walkthroughは、クライアントとサーバーの `ToyTcpEndpoint` を1つずつ作り、`run_three_way_handshake()` で両方を `ESTABLISHED` に到達させ、1つのデータセグメントを配送して受信側の `rcv_nxt` が進んだことを確認し、クライアント側から能動的closeを開始して `close()` → 相手の応答 → `TWO_MSL` を超える `tick()` まで、両エンドポイントが `CLOSED` になるまで駆動します。最後に、両エンドポイントの `trace` が空でなく、ハンドシェイクとcloseを示す行を含んでいることを確認します。出力はこうなります。

```text
Session 11 walkthrough: Build the toy TCP loop

[OK] handshake reaches ESTABLISHED -> client=Established server=Established
[OK] server delivers one data byte -> rcv_nxt 1002 -> 1003
[OK] client close() sends FIN      -> state=FinWait1
[OK] server hears FIN -> CLOSE_WAIT -> state=CloseWait
[OK] client hears ACK of our FIN   -> state=FinWait2
[OK] server close() sends FIN      -> state=LastAck
[OK] client hears server's FIN     -> state=TimeWait
[OK] server hears last ACK         -> state=Closed
[OK] one tick before TWO_MSL       -> state=TimeWait clock=239
[OK] tick reaches TWO_MSL          -> state=Closed clock=240
[OK] both endpoints CLOSED         -> client=Closed server=Closed
[OK] both traces non-empty         -> client=6 lines, server=7 lines
```

12行のうち、最初の1行がハンドシェイク、2行目がデータ配送、続く7行が能動的closeの一部始終（`FIN_WAIT_1` → 相手の `CLOSE_WAIT` → `FIN_WAIT_2` → 相手の `LAST_ACK` → 自分の `TIME_WAIT` → 相手の `CLOSED` → 時計が `TWO_MSL` に達して自分も `CLOSED`）、最後の2行が全体の整合性チェックです。`clock=239` で `TimeWait` のまま、`clock=240` で `Closed` に変わる ―― `TWO_MSL` という期限が1秒単位で厳密に効いていることが、この2行だけで確認できます。

各行の `[OK]` は、そのステップが**予想通りの状態遷移になった**という意味です。予想と食い違えば `[NG]` になります。特に7〜9行目の3ステップ（`server_fin` の受信、`TIME_WAIT`、`TWO_MSL` 到達）は、走らせる前に自分で `client.state` と `server.state` の値を紙に書き出してから確認すると、`_on_segment_teardown()` のディスパッチが体に入ります。

## この章を終えたと言える条件

ノートを見ずに、次を全部言えれば合格です。

- 「`ToyTcpEndpoint` の全フィールドは前の章のどれかに属する。この章の新しいコードは `on_segment()` の中の配線だけ」
- 「`state` は `ESTABLISHED` 前は `ConnectionState`、後は `CloseState` を保持する ―― 2つのenum空間が1つのフィールドに、意図して同居している」
- 「`on_reset()` は状態別の分岐より先に、無条件で走る。RSTは接続が何をしていようと同じ規則でチェックされる」

## この本を読み終えて

序章で、この本は3つの「同じ形」が何度も繰り返されると予告しました。ここで短く回収します。

**「期限つきの値」** は、第5章の再送タイマー（RTOが来たら退役する時刻つきの値）と、第9章のTIME_WAIT（`TWO_MSL` が来たら `CLOSED` に切り替わる時刻つきの値）に現れました。そしてこの章の `tick()` が、その2つ目の実例を最後まで動かして見せました ―― セグメントが何本届こうと、`TIME_WAIT` を終わらせるのは時計だけです。

**「沈黙は障害の合図」** は、第6章の高速再送（3つの重複ACKという「来たものの並び」からパケット消失を推測する）と、第5章のRTOタイムアウト（何も来ないこと自体を障害と読む）に現れました。この章では `_on_data()` の `track_ack()` が、その推測ロジックを実際のデータフローの中に組み込んだ形で残っています。

**「その数字は保存でなく計算」** は、第4章の受信ウィンドウ（`advertised_window()` が毎回その場で求める数字）と、第7章の輻輳ウィンドウ（`cwnd` が状態ではなく `on_ack()` / `on_timeout()` の結果として更新される数字）に現れました。この章で `on_reset()` が呼ぶ `advertised_window(self.recv_buffer)` は、その「保存でなく計算」を、RSTの正当性チェックという新しい文脈でもう一度使っています。

3つのテーマが繰り返し出てきたのは偶然ではありません。TCPは「10個の別々の仕組み」ではなく、「期限」「沈黙からの推測」「その場の計算」という少数のアイデアを、セグメント・ウィンドウ・タイマー・状態機械という異なる材料に何度も適用したものです。`speaker.py` がやったことは、その少数のアイデアを新しく発明することではなく、10章分の実装を1つのオブジェクトの中で**同時に**動かして見せることでした。

コードを読み終えたということは、次に実物のTCPスタック ―― Linuxカーネルの `tcp_input.c` でも、RFC 9293 の状態遷移図でもいい ―― を開いたときに、「これは何をしているコードか」を問える準備ができた、ということです。おもちゃはここで終わりますが、読み方は終わりません。
