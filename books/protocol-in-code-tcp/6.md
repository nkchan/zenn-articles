## この章の問い

TCPは、セグメントを送ってから「もう届かなかった」と判断するまで、何ミリ秒待てばいいのか。その答えは固定値ではありません。ネットワークのRTT（往復時間）は毎回揺れるのに、TCPはどうやって**その揺れに合わせて**待ち時間を調整しているのか。

この章を読み終えると、次のことが言えるようになります。

- 最初のRTTサンプルだけが、それ以降のサンプルと**まったく違う扱い**を受ける理由を説明できる
- RTOの計算式を言え、どの項が「平均の遅さ」ではなく「揺れの大きさ」に反応させているかを指摘できる
- なぜRTOは計算しっぱなしではなく、上限と下限で挟まれているのかを説明できる
- タイムアウトが2回、3回、4回と連続したとき、タイマーに何が起きるかを説明できる

対応するソースファイルは `src/protocol_in_code/tcp/rto.py` です。

## RTOは「保存されている数字」ではなく「毎RTT計算し直される数字」

この章は、序章で触れた本書のテーマ「期限つきの値 ―― 時刻を持ち、時が来たら切り替わる」の、最もわかりやすい実例です。RTO（Retransmission Timeout、再送タイマー）は固定の秒数ではありません。ACKが返ってくるたびに、TCPは「今回の往復にどれだけかかったか」を1サンプルとして観測し、それを使ってタイマーの長さそのものを**学習し直します**。

まず、この学習結果を保持する型を見ます。

```python
MIN_RTO_MS = 1_000
MAX_RTO_MS = 60_000


@dataclass
class RttEstimator:
    srtt: float | None = None
    rttvar: float = 0.0
```

フィールドは2つだけです。

| フィールド | 意味 |
|---|---|
| `srtt` | 平滑化された往復時間（Smoothed RTT）。`None` は「まだ一度もサンプルが来ていない」という意味そのもの |
| `rttvar` | サンプルが `srtt` からどれだけ外れて動いているかを平滑化した値。ネットワークが「遅い」のではなく「揺れている」ときに、この値がRTOを広げる |

`srtt: float | None` ―― この `None` はバグへの防御ではなく、`observe()` が分岐に使う**信号そのもの**です。「一度も観測していない」という状態を、わざわざ別のフラグで持たせず、`srtt` 自身の値で表現しています。

## `observe()` ―― 最初のサンプルと、それ以降のサンプルはコードパスが違う

```python
def observe(estimator: RttEstimator, sample_ms: float) -> None:
    """The timer learns the network: each RTT sample nudges a smoothed estimate, Jacobson/Karels style."""
    if estimator.srtt is None:
        # RFC 6298 2.2: first measurement seeds srtt directly, rttvar to half of it.
        estimator.srtt = sample_ms
        estimator.rttvar = sample_ms / 2
        return

    # RFC 6298 2.3: rttvar tracks how much the sample disagreed with the running estimate.
    estimator.rttvar = 0.75 * estimator.rttvar + 0.25 * abs(estimator.srtt - sample_ms)
    estimator.srtt = 0.875 * estimator.srtt + 0.125 * sample_ms
```

この関数には、`estimator.srtt is None` を境に**完全に別の2つの経路**があります。

**種まき（seeding）の分岐** ―― `RttEstimator` の一生で一度しか通りません。最初のサンプルをそのまま `srtt` に代入し、`rttvar` はその半分に設定します（RFC 6298 2.2節）。「平均」も「分散」もまだ計算しようがないので、最初の1サンプルを暫定の基準点として受け入れる、という判断です。

**更新（EWMA）の分岐** ―― 2回目以降の全呼び出しがここを通ります。EWMA（指数移動平均、Exponentially Weighted Moving Average）で `srtt` と `rttvar` を少しずつ書き換えます。

ここで、この章で一番丁寧に読むべき箇所が出てきます。**2行の代入の順序**です。

```python
estimator.rttvar = 0.75 * estimator.rttvar + 0.25 * abs(estimator.srtt - sample_ms)
estimator.srtt = 0.875 * estimator.srtt + 0.125 * sample_ms
```

1行目で `rttvar` を更新するとき、使われているのは**まだ更新されていない古い `srtt`** です。もし順序を逆にして先に `srtt` を書き換えてしまうと、`rttvar` の計算に使われるのは今回のサンプルで既に動いた後の新しい `srtt` になり、「サンプルが基準からどれだけ外れていたか」という本来の意味が壊れます。コードの見た目は2行の代入に過ぎませんが、順序そのものが仕様です。

式の意味を分解します。

- `rttvar = 0.75 * rttvar + 0.25 * |srtt - sample|` ―― 「古い `srtt`」と「今回のサンプル」の差の絶対値を、これまでの `rttvar` に25%だけ混ぜ込みます。差が大きい（＝サンプルが暴れた）ほど `rttvar` は押し上げられ、差が0（＝サンプルが `srtt` にぴったり一致）なら `rttvar` は0.75倍に減衰していきます。つまり `rttvar` は「最近のサンプルはどれだけ暴れているか」を追いかける値です。
- `srtt = 0.875 * srtt + 0.125 * sample` ―― 新しいサンプルを12.5%だけ混ぜて、古い推定値を87.5%残します。1回の外れ値で `srtt` が大きく動かないようにする、平均のなだらかな更新です。

`0.75/0.25` と `0.875/0.125` という重みは、Jacobson/Karels アルゴリズム（RFC 6298の元になった手法）が経験的に定めた値で、コード中にマジックナンバーとしてそのまま埋め込まれています。

## `rto()` ―― RTOは「平均」ではなく「平均＋揺れ」

```python
def rto(estimator: RttEstimator) -> int:
    """RTO = srtt + 4*rttvar, clamped so the timer is never absurdly tight or absurdly loose."""
    if estimator.srtt is None:
        return MIN_RTO_MS

    computed = estimator.srtt + 4 * estimator.rttvar
    return int(min(MAX_RTO_MS, max(MIN_RTO_MS, computed)))
```

式はただ一つ、`srtt + 4 * rttvar` です。この `4*` が、この章の核心です。RTOは「平均往復時間がどれだけか」だけでなく「**サンプルがどれだけ暴れているか**」にも反応します。安定して100msで往復し続けるネットワークと、20msと180msの間を行き来する不安定なネットワークは、`srtt` が同じ値に収束していても `rttvar` がまったく違い、結果として `rto()` は大きく異なる値を返します。揺れの大きいネットワークほど、RTOには余裕を持たせる ―― これが `4*rttvar` の役割です。

そして、`estimator.srtt is None` のときは `MIN_RTO_MS` を返す早期リターンがあり、サンプルがある場合の計算結果も含めて、最終的に必ず同じ `min(MAX_RTO_MS, max(MIN_RTO_MS, ...))` のクランプを通ります。計算結果をそのまま信じるのではなく、「どれだけ短くても1秒」「どれだけ長くても60秒」という下限・上限に必ず挟み込む。ネットワークがどれだけ安定していても再送タイマーが数十ミリ秒まで縮んで誤送出を連発することはなく、どれだけ荒れていても1分を超えて実質無反応になることもありません。

## `on_timeout()` ―― 推定値には触らない、今のRTOを2倍にするだけ

```python
def on_timeout(current_rto_ms: int) -> int:
    """RFC 6298 5.5: back off exponentially on every consecutive timeout, capped at MAX_RTO."""
    return min(MAX_RTO_MS, current_rto_ms * 2)
```

1行だけの指数バックオフです。ここで見落としやすいのは、この関数が `RttEstimator` にまったく触れていないという点です。`srtt` も `rttvar` も読みも書きもしません。タイムアウトが起きても、`observe()` で学習してきた「ネットワークの体感」自体は変更されない ―― タイムアウト後の次のRTOは、`srtt`/`rttvar` から**再計算されるのではなく、直前のRTOを単純に2倍にしたもの**です。

そしてこの関数は「現在のRTOが何ミリ秒か」という状態を一切保持していません。呼び出し側が `current_rto_ms` として毎回渡す必要があります。連続タイムアウトを3回重ねたいなら、呼び出し側が前回の戻り値を次の呼び出しに渡し続ける責任を負います。推定器は「タイムアウトが起きたこと」自体を知らないままです。

## 決定フローのまとめ

```text
srtt is None                -> 種まき: srtt = sample, rttvar = sample / 2
srtt is not None            -> 更新: rttvar を先に(古いsrttから)、次にsrtt
rto() でサンプル無し        -> MIN_RTO_MS
rto() でサンプルあり        -> clamp(srtt + 4*rttvar, MIN_RTO_MS, MAX_RTO_MS)
on_timeout()                -> clamp(現在のrto * 2, ..., MAX_RTO_MS)
```

## おもちゃの境界

実物のTCPスタックはKarnのアルゴリズムを適用します。再送されたセグメントから得たRTTサンプルは、どちらのコピーに対するACKなのか区別できないため、決して信用しません。このおもちゃの `observe()` は `sample_ms` を額面通り受け取るだけで、「このセグメントは再送だったか」という概念を一切持たないので、悪いサンプルを渡せば無防備に `srtt` を汚染します。実物のプロトコルにはTCPタイムスタンプオプション（RFC 7323）もあり、ACKのタイミングからRTTを推測する代わりにタイムスタンプをそのまま送り返すことで、この曖昧さ自体を回避しています。このおもちゃにそのオプションはありません。

ここでの RTO は `(srtt, rttvar)` と2つの定数だけの純粋関数です。再送回数を状態として持ち回してどこかにフィードバックする仕組みは `on_timeout()` の倍加以外になく、その倍加結果自体もどこにも保存されません ―― 呼び出し側が現在のRTOを呼び出しをまたいで覚えておく責任を負います。

## 自分で答える問い

ソースファイルを見て答えてください（docstring ではなく関数の本体で）。

1. `observe()` が一度も呼ばれないとき、`rto()` は何を返すか。それを保証しているのはソースのどの行か。
2. `observe()` の2回目の呼び出しで、`rttvar` の計算に使われる `srtt` は、その同じ呼び出しで更新される**前**の値か、**後**の値か。
3. 2つの推定器がどちらも `srtt = 900` に収束している。一方は `rttvar = 5`、もう一方は `rttvar = 50`。`rto()` はどちらが大きくなるか、差はいくつか。（クランプが最初の推定器に何をするかに注意。）
4. まっさらな推定器に8msのサンプルを1つ与える。`srtt + 4*rttvar` を計算すると24になる。`rto()` は実際に何を返すか、どの定数がそれを決めているか。
5. `on_timeout(1500)` から始めて、前回の戻り値を毎回渡しながら3回連続で呼び出すと結果はどうなるか。3回分の掛け算はどの1行が担っているか。

（問い1の答えの入口: `estimator.srtt is None` が真のとき `rto()` は早期リターンで `MIN_RTO_MS` を返す。EWMAの分岐にも `srtt + 4*rttvar` の計算にも一度も入らない。）

## 動かして確認する

```bash
PYTHONPATH=src python3 examples/tcp/session_05_walkthrough.py
```

walkthroughは、1サンプルで推定器を種まきし、安定したサンプルを連続で与えてRTOが締まっていく様子を確認し、1つだけスパイクしたサンプルを注入してRTOが広がる様子を確認し、最後に `on_timeout()` でタイマーを2回倍加します ―― 1回は通常通り、もう1回は既に上限に達している状態からです。

実際の出力は次の通りです。

```text
Session 05 walkthrough: The timer learns the network

[OK] no samples yet              -> rto=1000ms
[OK] first sample seeds estimator -> srtt=800 rttvar=400.0 rto=2400ms
[OK] stable network tightens rto  -> srtt=800.0 rttvar=94.9 rto=1179ms
[OK] one spiky sample widens rto  -> srtt=1075.0 rttvar=621.2 rto=3559ms
[OK] timeout doubles the timer    -> rto 3559ms -> 7118ms
[OK] doubling is capped at max     -> rto 60000ms -> 60000ms
```

各行の `[OK]` は、「その操作の結果が予想通りだった」という意味です。数字を1行ずつ追うと式の意味が体に入ります。

- 1行目: サンプルなしなので `MIN_RTO_MS` の1000msがそのまま出る。
- 2行目: 最初のサンプル800msが種まきの分岐を通り、`srtt=800`、`rttvar=400`（800の半分）。`rto = 800 + 4*400 = 2400`。
- 3行目: 800msを5回連続で観測。サンプルが `srtt` と完全一致し続けるので `rttvar` は呼ぶたびに0.75倍ずつ減衰し（400→300→225→168.75→126.5625→94.921875）、`srtt` は800のまま動かない。`rto = 800 + 4*94.9 ≈ 1179`。ネットワークが安定しているほどRTOが締まっていくのが読み取れる。
- 4行目: そこに3000msのスパイクを1つ混ぜると、`srtt` は `0.875*800 + 0.125*3000 = 1075`、`rttvar` は `0.75*94.9 + 0.25*|800-3000| = 621.2` まで跳ね上がる。`rto = 1075 + 4*621.2 ≈ 3559`。たった1サンプルの乱れが `rttvar` を通じてRTOを大きく押し上げることがわかる。
- 5行目: `on_timeout(3559)` は単純に2倍の7118。`srtt`/`rttvar` の値は一切参照されていない。
- 6行目: 既に `MAX_RTO_MS`（60000）にいる状態で `on_timeout()` を呼んでも、2倍した後にクランプされて60000のまま ―― 上限で頭打ちになることが確認できる。

## この章を終えたと言える条件

ノートを見ずに、次を全部言えれば合格です。

- 「最初のサンプルが推定器の種をまき、それ以降のサンプルは全て 7/8 + 1/8 と 3/4 + 1/4 の重みで少しずつ動かす」
- 「RTOはサンプルの大きさそのものではなく、サンプルがどれだけ食い違っているかに反応する ―― それが `rttvar` と `4*` の役目」
- 「タイムアウトは今のRTOを2倍にするだけで、`srtt`/`rttvar` から計算し直しているわけではない」

次章では、このタイマーが**満了するのを待たずに**損失を検知する経路を読みます。重複ACKが3回続くことは「失われた」の合図になる ―― `fast_retransmit.py` を開き、タイムアウトを待たずにACKの並びだけから損失を推測する仕組みを見ます。
