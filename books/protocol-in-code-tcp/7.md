## この章の問い

送信側は、再送タイマーの満了を待たずに、ACKだけを見て「セグメントが失われた」とどう判断するのか。そして、なぜその判断のトリガーは「重複ACKが2回」でも「4回」でもなく、**ちょうど3回**なのか。

この章を読み終えると、次のことが言えるようになります。

- 「重複ACK」とは何か ―― 単に「同じ値が繰り返された」ではなく、**どの値が繰り返されたか**で説明できる
- どの繰り返し回数で信号が高速再送に切り替わるかを、正確に言える
- 同じackの4回目の繰り返しが、2度目の高速再送トリガーに**ならない**理由を説明できる
- 何が重複カウンタをリセットするか、そしてそれが「新しいデータがACKされた」という出来事と**同じ分岐**であることを説明できる

対応するソースファイルは `src/protocol_in_code/tcp/fast_retransmit.py` です。

## 沈黙は障害の合図 ―― この章はその代表例

序章で触れた、この本を貫くテーマを覚えているでしょうか。「パケットが**来ない**ことを、来たパケットから推測する」。この章はその最も分かりやすい実例です。

失われたセグメントそのものは、送信側には決して見えません。届かなかったものは届かなかったのだから、当然です。送信側に見えるのは、届き**続けている**ACKだけです。しかもそのACKは、奇妙なことに**同じ値を繰り返す**。前に進むはずのACKが、なぜか足踏みしている ―― この足踏みこそが、送信側が手にできる唯一の手がかりです。

再送タイマー（第5章の `rto.py`）も同じ発想でした。「時間が来ても何も届かない」ことを合図にしていた。この章の高速再送は、それより速い経路です。タイマーが切れるのを待たずに、**ACKの繰り返しパターンだけ**から損失を読み取ります。

## 3つのフィールドと1つの定数

読む対象は驚くほど小さいファイルです。

```python
DUP_ACK_THRESHOLD = 3


class AckSignal(str, Enum):
    NEW_DATA_ACKED = "NewDataAcked"
    DUPLICATE = "Duplicate"
    FAST_RETRANSMIT = "FastRetransmit"


@dataclass
class AckTracker:
    last_ack: int = 0
    dup_count: int = 0
```

`AckTracker` はたった2つのフィールドしか持ちません。

| フィールド | 意味 |
|---|---|
| `last_ack` | 直近に見たack値。新しく届いたackは、常にこれと比較される。「これまで見た最大のack」でも、ウィンドウの状態でもない |
| `dup_count` | 現在の `last_ack` が**連続して**何回繰り返されたか。ackの値が変われば0にリセットされる |

`AckSignal` は3つの値しか持ちません。「まだ様子見」も「不明」もない ―― `on_ack()` を1回呼べば、必ずこの3つのうちどれか1つが返ります。曖昧さの余地がない設計です。

そして `DUP_ACK_THRESHOLD = 3`。TCPにまつわる「3回重複ACKで再送」という語り継がれた知識は、結局のところ、**この定数がどこか1箇所の比較で1回読まれるだけ**に集約されます。

## `on_ack()` ―― この章の本命

```python
def on_ack(tracker: AckTracker, ack: int) -> AckSignal:
    """Three duplicates mean loss: the third repeat of the same ack triggers fast retransmit."""
    if ack != tracker.last_ack:
        tracker.last_ack = ack
        tracker.dup_count = 0
        return AckSignal.NEW_DATA_ACKED

    tracker.dup_count += 1

    if tracker.dup_count == DUP_ACK_THRESHOLD:
        return AckSignal.FAST_RETRANSMIT

    return AckSignal.DUPLICATE
```

短い関数ですが、読みどころが3つ詰まっています。

**1. リセットは比較より先に起きる。** `ack != tracker.last_ack` が真なら、`dup_count` に触れる前に即座に0へ戻り、`last_ack` を新しい値で上書きして `NEW_DATA_ACKED` を返します。「新しいデータがACKされた」と「重複カウンタがリセットされた」は、**別々のイベントではなく同じ1つの分岐**です。ここを2つの独立した処理だと思っていると、この関数の設計意図を読み損ないます。

**2. カウントは `!=` の否定側でだけ増える。** `ack == tracker.last_ack` の側に落ちて初めて `dup_count += 1` が走ります。つまり `dup_count` が指しているのは「これまで見たackの総数」でも「重複の累積」でもなく、**「今の `last_ack` が連続して何回繰り返されたか」**だけです。

**3. 比較は `==` であって `>=` ではない。** ここが核心です。`tracker.dup_count == DUP_ACK_THRESHOLD` という**厳密な等号**が、高速再送を「一度きりのエッジ」にしています。3回目の重複でぴったり3になった瞬間だけ `FAST_RETRANSMIT` が返る。4回目の重複が来ると `dup_count` は4になり、`4 == 3` は偽なので `DUPLICATE` に落ちます。もしこれが `>=` だったら、同じ喪失に対して4回目、5回目、6回目……と際限なく再送信号が出続けることになります。`==` は、「一度トリガーしたら、次に新しいことが起きるまでは黙る」という振る舞いを、たった1文字の演算子で実現しています。

## 判断の流れ

```text
ack != tracker.last_ack        -> NEW_DATA_ACKED  (last_ack を更新、dup_count は 0 にリセット)
ack == tracker.last_ack:
    dup_count += 1
    dup_count == DUP_ACK_THRESHOLD (3)  -> FAST_RETRANSMIT
    それ以外                             -> DUPLICATE
```

この図だけを見て「3回重複したら再送」と丸暗記するのは簡単です。しかしこの章で本当に押さえるべきは、次の4つの問いに正確に答えられるかどうかです。

- この比較は `==` か `>=` か。（4回目、5回目、6回目の繰り返しで挙動が変わる）
- `FAST_RETRANSMIT` が返る**その瞬間**、`dup_count` は正確にいくつを保持しているか
- 現在の `last_ack` **より前**の値が繰り返された場合、それは何かにカウントされるのか、それとも単に `last_ack` と比較されて終わりか
- `FAST_RETRANSMIT` の直後に同じackがもう一度届いたら、次の `AckSignal` は何になるか

## なぜ「3回」なのか ―― 順序入れ替えとの区別

なぜ1回や2回の重複では動かず、3回まで待つのか。答えは、ネットワークでは**パケットの順序が入れ替わることがある**からです。

セグメントが1つ、ネットワーク経路の途中で他のセグメントを追い越されて遅延しただけなら、受信側は「まだ次の連続バイトが来ていない」として、直前と同じackを1回か2回返すことがあります。しかしその遅れていたセグメントが到着すれば、ackはすぐに前進します。これは損失ではなく、ただの順序の乱れです（順序の乱れそのものの吸収は第8章の主題です）。

もし `DUP_ACK_THRESHOLD` が1だったら、単なる順序入れ替えのたびに不要な再送が発生してしまいます。3回という閾値は、「1、2回の重複は順序入れ替えの範囲内かもしれないが、3回連続で同じackが返ってくるなら、単なる遅延ではなく本当にそのセグメントが失われた可能性が高い」という経験的な線引きです。`AckTracker` はこの判断の根拠（順序入れ替えか損失か）を一切知りません。知っているのは「同じ値が何回連続したか」という事実だけです。しかしその1つの数字の閾値だけで、実用上十分に損失と順序入れ替えを区別できる ―― これがRFC 5681が定めた設計判断であり、このモジュールはそれをそのままコードに落としたものです。

## おもちゃの境界

実物のTCP受信側は、SACK（Selective Acknowledgment, RFC 2018）を使えば、**どのブロックのデータが届いているか**を送信側に正確に伝えられます。送信側は1回の重複ackから「どのセグメントが欠けているか」を推測する必要がなく、欠けている部分だけを即座に特定して再送できます。

このおもちゃにSACKはありません。`on_ack()` が見るのは常に単一の整数ack値だけで、正確な繰り返し回数を数えるだけです。3回の重複ackが「受信側が3つの異なるセグメントを受け取ったが、どれも同じ次期待バイトをackしている」のか、「3つの別々の小さな損失が起きている」のかを、この実装は区別できません。ただ数えるだけです。

また、ackがウィンドウ情報やタイムスタンプを運ぶという概念もここにはなく、第5章のRTOタイマーとの連携もありません。`AckTracker` は、ack値のストリームに対する純粋なカウンタでしかありません。

## 自分で答える問い

ソースファイルを見て答えてください（docstring ではなく関数の本体で）。

1. 同じackがちょうど3回目の重複をした瞬間、`on_ack()` は何を返し、そのすぐ後の `tracker.dup_count` はいくつか。
2. `FAST_RETRANSMIT` をトリガーした後、同じackが4回目も繰り返されたら、`on_ack()` は今度は何を返すか。それが2度目の `FAST_RETRANSMIT` にならない理由は、どの行に書かれているか。
3. ackが2回重複して（`dup_count` が2に達して）、そのあとに本当に新しいack値が届いたら、`on_ack()` は何を返し、`last_ack` と `dup_count` はその後どうなるか。
4. `AckTracker()` は `last_ack` のデフォルトを `0` にしている。送信側が最初に実際に見るackもたまたま `0` だったら、`on_ack()` は何を返すか。なぜこのフィールドのデフォルト値が問題になり得るのか。
5. もし `DUP_ACK_THRESHOLD` が `1` に変更されたら、最初の1回の重複で `on_ack()` は何を返すようになるか。どの行の比較がそれを決めるか。

（問い1の答えの入口: 3回目の重複で `dup_count += 1` が実行された直後、`tracker.dup_count` は3になる。`3 == DUP_ACK_THRESHOLD` が真になるので `on_ack()` は `AckSignal.FAST_RETRANSMIT` を返す。）

## 動かして確認する

```bash
PYTHONPATH=src python3 examples/tcp/session_06_walkthrough.py
```

walkthroughは、ackを1回送り、同じ値を3回繰り返して `DUPLICATE, DUPLICATE, FAST_RETRANSMIT` の流れを確認し、さらに4回目の繰り返しで信号が `DUPLICATE` に戻ることを見せ、最後に新しいデータのackでカウンタがリセットされ、新しい重複カウントが1から再スタートすることを確認します。実際の出力はこうなりました。

```text
Session 06 walkthrough: Three duplicates mean loss

[OK] first ack for 1000            -> NewDataAcked dup_count=0
[OK] repeat #1                     -> Duplicate dup_count=1
[OK] repeat #2                     -> Duplicate dup_count=2
[OK] repeat #3 hits the threshold  -> FastRetransmit dup_count=3
[OK] repeat #4 is not a re-trigger -> Duplicate dup_count=4
[OK] new data resets the counter   -> NewDataAcked dup_count=0 last_ack=2000
[OK] counting starts over from 1   -> Duplicate dup_count=1
```

`[OK]` は、そのackが**予想通りの `AckSignal` と `dup_count`（場合によっては `last_ack`）になった**という意味です。予想と食い違えば `[NG]` になります。特に4行目から5行目の遷移 ―― `dup_count=3` で `FastRetransmit` が出た直後、同じackがもう一度来ても `dup_count=4` で `Duplicate` に落ちる ―― を、自分の頭で先に予想してから実行結果と突き合わせてみてください。`==` と `>=` の違いが、ここで初めて実感として身体に入ります。

## この章を終えたと言える条件

ノートを見ずに、次を全部言えれば合格です。

- 「同じackの3回の重複が高速再送を引き起こす ―― `==` によるちょうど3回目のトリガーであって、`>=` による4回目以降の連続トリガーではない」
- 「4回目の繰り返しは2度目の高速再送信号ではなく、ただのもう1つの重複でしかない」
- 「`last_ack` と異なるack値はどれも `dup_count` を0にリセットする ―― それは `NEW_DATA_ACKED` を返すのと同じ分岐である」
- 「3回という閾値は、単なる順序入れ替えと本当の損失を区別するための経験的な線引きであり、`AckTracker` 自身はその区別の理由を知らず、ただ回数を数えているだけである」

次章では、視点をackの数え上げから**もう1つの整数**に移します。第7章では `congestion.py` を開き、輻輳ウィンドウ `cwnd` を読みます。cwndは状態としてどこかに保存された神秘的な値ではなく、ただの整数変数です。輻輳制御とは、その整数を上下させる数個の規則にすぎないのか ―― それを確かめます。
