## この章の問い

輻輳制御は「アルゴリズム」という肩書きで語られがちです。スロースタート、輻輳回避、ファストリカバリ ―― どれも名前だけ聞くと重厚な仕組みに見える。しかしコードとして読んだとき、それは本当にアルゴリズムと呼ぶべき複雑さを持っているのか。それとも、**1個の整数を上げ下げする数個の規則**にすぎないのか。

この章を読み終えると、次のことが言えるようになります。

- スロースタートと輻輳回避のどちらのフェーズにいるかを決める、たった1つの比較を言える
- スロースタートが `cwnd` を「倍にする」のではなく「ACK 1つにつき1MSSずつ足す」実装になっている理由を説明できる
- 輻輳回避が1MSS成長するのに、なぜ `cwnd` 個分のACKをまるごと必要とするのかを説明できる
- 同じ状態から出発したとき、タイムアウトとファスト再送が `cwnd` と `ssthresh` に対してそれぞれ何をするかを対比できる

対応するソースファイルは `src/protocol_in_code/tcp/congestion.py` です。

## `cwnd` は3つの整数のうちの1つ

まず、この章が扱う型そのものを見ます。

```python
INITIAL_CWND = 1


class CongestionPhase(str, Enum):
    SLOW_START = "SlowStart"
    CONGESTION_AVOIDANCE = "CongestionAvoidance"


@dataclass
class CongestionState:
    """cwnd is just a variable: every branch below is a rule for how one integer moves."""

    cwnd: int = INITIAL_CWND
    ssthresh: int = 64
    acks_in_round: int = 0
```

`CongestionState` はフィールド3つの、ただのデータクラスです。

| フィールド | 意味 |
|---|---|
| `cwnd` | 輻輳ウィンドウ。単位はMSS（バイト数ではなく、セグメント個数を数える整数）。この章の他のすべては、この数字を動かすために存在する |
| `ssthresh` | スロースタート閾値。ハードな上限ではなく、`phase()` が `cwnd` と比較する**境界線**にすぎない |
| `acks_in_round` | 輻輳回避フェーズでしか意味を持たないカウンタ。「cwnd個分のACKが揃った」ことを、割り算も端数計算もせずに数えるための仕組み |

第1章で `Segment` が `frozen=True` の不変データクラスだったのに対し、ここでは可変です。理由は単純で、`cwnd` は接続が続く間ずっと**変わり続ける**数字だからです。第1章で見た「セグメントは書き換えない」という規律と、この章の「状態は絶えず書き換える」という規律は矛盾しません。どちらも、**何を不変にして何を可変にするかを、意図的に選んでいる**という同じ設計思想の両面です。

## `phase()` ―― キャッシュされない1つの比較

```python
def phase(state: CongestionState) -> CongestionPhase:
    if state.cwnd < state.ssthresh:
        return CongestionPhase.SLOW_START
    return CongestionPhase.CONGESTION_AVOIDANCE
```

これがこの章の核です。`phase()` は `cwnd < ssthresh` という**1つの比較**でしかありません。副作用は無く、`CongestionState` のどこにも「現在のフェーズ」を保存するフィールドはありません。つまりフェーズは**状態として持たれているのではなく、毎回その場で計算されている**。

この点は序章のテーマそのものです ―― 「その数字は保存されていない、計算されている」。ウィンドウや輻輳ウィンドウだけでなく、**フェーズという分類そのもの**も同じ扱いを受けています。`on_ack()` がフェーズを見たいときも、外部からこの状態を覗きたいときも、毎回 `phase()` を呼び直す。どこかにキャッシュされた `self.phase` のようなフィールドを探しても、存在しません。

ここで押さえておきたい境界条件が1つあります。`cwnd == ssthresh` のとき、比較演算子は `<` であって `<=` ではないので、この場合は `CONGESTION_AVOIDANCE` 側に落ちます。「等しくなった瞬間」がスロースタート側に残るのか輻輳回避側に移るのか ―― この演算子1文字が、その答えを決めています。

## `on_ack()` ―― フェーズで分岐する、たった2つの規則

```python
def on_ack(state: CongestionState) -> CongestionPhase:
    """Slow start doubles cwnd per round trip (one MSS per ack); avoidance adds one MSS per round trip."""
    current_phase = phase(state)

    if current_phase is CongestionPhase.SLOW_START:
        state.cwnd += 1
        state.acks_in_round = 0
        return current_phase

    # Congestion avoidance: only after a full cwnd's worth of acks do we grow by one MSS.
    state.acks_in_round += 1
    if state.acks_in_round >= state.cwnd:
        state.cwnd += 1
        state.acks_in_round = 0
    return current_phase
```

冒頭で `phase()` を1回だけ呼び、結果で分岐します。分岐は2つしかありません。

**スロースタート側**は無条件です。ACKを1つ受け取るたびに `cwnd += 1`。「倍にする」というスロースタートの評判とは裏腹に、コードは足し算しかしていません。倍増に見えるのは、1往復（1 round trip）の間に送り出したセグメントの数だけACKが返ってきて、そのACK1つひとつが `on_ack()` を1回ずつ呼ぶからです。つまり倍増は**このコードの性質ではなく、往復という外側の構造から生まれる結果**にすぎません。`on_ack()` 自身は「往復」という概念を一切知らず、ACK単発の到着しか見ていません。`acks_in_round` もこの分岐では意味を持たないのに、念のため0にリセットしています。

**輻輳回避側**は条件付きです。`acks_in_round` を毎回1つ増やし、それが `cwnd` 以上になった瞬間だけ `cwnd += 1` してカウンタを0に戻す。これは「ACK1つにつき1/cwnd MSSずつ増える」という分数的な成長を、割り算を使わずに**整数の積み上げ**で表現したものです。「cwnd個分のACKが1周してはじめて、次の1段に上がる」と読むのが正確で、ACK単発ごとの端数成長ではありません。

## `on_timeout()` と `on_fast_retransmit()` ―― 同じ計算、違う着地点

```python
def on_timeout(state: CongestionState) -> None:
    """A timeout means the network is more congested than we assumed: halve, then restart small."""
    state.ssthresh = max(state.cwnd // 2, 2)
    state.cwnd = INITIAL_CWND
    state.acks_in_round = 0


def on_fast_retransmit(state: CongestionState) -> None:
    """Fast recovery (simplified): halve ssthresh, but resume right at that new ceiling, not from 1."""
    state.ssthresh = max(state.cwnd // 2, 2)
    state.cwnd = state.ssthresh
    state.acks_in_round = 0
```

2つの関数は、`ssthresh` の計算式が**完全に同じ**です。どちらも `max(cwnd // 2, 2)` ―― 現在の `cwnd` を半分にし、下限2を割らないようにする。`max()` の2番目の引数が効いてくるのは `cwnd` が2か3のときで、`cwnd // 2` がそれぞれ1か1になり、そのままだと `ssthresh` が1まで落ちてしまう。それを防いでいるのがこの `2` という定数です。

違うのは `cwnd` の**着地点**だけです。`on_timeout()` は `cwnd` を `INITIAL_CWND`（1）まで叩き落とし、スロースタートからやり直させる。`on_fast_retransmit()` は `cwnd` を、たった今計算したばかりの `ssthresh` に**そのまま**セットします。第6章で読んだ「3つの重複ACKは喪失のサイン」という判断と、タイムアウトという判断は、どちらも「パケットが失われた」という結論に至る点では同じですが、その後どれだけ強く回復を絞るかがまったく違う ―― タイムアウトは「何も分からない」に近い状態なので最初からやり直し、ファスト再送は「重複ACKが来ている＝一部のセグメントはまだネットワークを流れている」という情報があるぶん、そこまで悲観的にならない。同じ `ssthresh` の計算式の後ろに、この非対称な着地点の違いが隠れています。

## おもちゃの境界

RFC 5681 の本物のファストリカバリは、これよりずっと手が込んでいます。回復中に重複ACKを1つ受け取るごとに `cwnd` を一時的にさらに膨らませ（ネットワークから抜けたセグメント分を補うため）、再送したセグメントがACKされた時点で `ssthresh` まで縮め直す ―― という「膨張してから収縮する」2段階の動きをします。このおもちゃの `on_fast_retransmit()` は、その膨張を丸ごと省略し、1回の呼び出しで `cwnd = ssthresh` に直接ジャンプします。「回復に入った直後」と「まだ回復中」を区別する状態も、このコードには存在しません。

スロースタートも同様に単純化されています。「ACK1つにつき1MSS」という規則が結果的に「1往復でcwndが倍になる」ように見えるのは、その往復で送ったセグメントすべてがACKされ、かつそのACKが1つずつ別々に `on_ack()` へ渡されたときに限られます。コード自身は「往復」という概念を一度も持たず、ACKの個数を数えているだけです。遅延ACKの勘定も、ECNも無く、`cwnd` はバイト数ではなくMSS単位の無次元の整数なので、実物のスタックがしばしば使うバイト単位の輻輳回避も、このおもちゃにはありません。

## 自分で答える問い

ソースファイルを見て答えてください（docstring ではなく関数の本体で）。

1. `cwnd == ssthresh` のとき、`phase()` はどちらのフェーズを返すか。それを決めている比較演算子はどれか。
2. 輻輳回避中、`cwnd = 4` かつ `acks_in_round = 3` のとき、次の `on_ack()` は両方のフィールドに何をするか。もし `acks_in_round` が2だったら何が変わるか。
3. `CongestionState(cwnd=10, ssthresh=20)` から出発したとき、`on_timeout()` の後の `cwnd` と `ssthresh` はいくつか。同じ出発点から `on_fast_retransmit()` を呼んだ場合はどうか。どちらのフィールドが両方の結果で一致するか。
4. `on_timeout()` は `ssthresh = max(cwnd // 2, 2)` を計算する。タイムアウトの瞬間に `cwnd` が2または3だったら `ssthresh` はいくつになり、`max()` のどちらの項が効いているか。
5. スロースタート中、`on_ack()` は `acks_in_round` をリセット以外の理由で読んだり書いたりしているか。それは、スロースタートの成長がこのフィールドに一切依存しないことを意味するか。

（問い1の答えの入口: `phase()` の条件は `state.cwnd < state.ssthresh` であって `<=` ではない。だから等しくなった瞬間、条件は偽になり `CONGESTION_AVOIDANCE` が返る。）

## 動かして確認する

```bash
PYTHONPATH=src python3 examples/tcp/session_07_walkthrough.py
```

walkthroughは、`cwnd=1, ssthresh=4` の状態からACKを1つずつ与えてスロースタートで `cwnd` を伸ばし、`cwnd == ssthresh` になった瞬間にフェーズが切り替わることを確認し、続けて輻輳回避の「ACKを数える」振る舞いを追います。そのうえで、同じ出発状態を2つに複製し、片方はタイムアウト経路、もう片方はファスト再送経路に分岐させて、着地点の違いを対比します。出力はこうなります。

```text
Session 07 walkthrough: cwnd is just a variable

[OK] starts in slow start          -> cwnd=1 ssthresh=4 phase=SlowStart
[OK] one MSS per ack while cwnd<ss -> cwnd trace=[1, 2, 3, 4]
[OK] cwnd==ssthresh flips the phase -> cwnd=4 ssthresh=4 phase=CongestionAvoidance
[OK] avoidance counts acks, not cwnd yet -> cwnd=4 acks_in_round=1
[OK] avoidance needs cwnd acks     -> cwnd=4 acks_in_round=3
[OK] a full round grows by one MSS -> cwnd=5 acks_in_round=0
[OK] timeout collapses cwnd to 1   -> cwnd=1 ssthresh=5
[OK] fast retransmit lands at ssthresh -> cwnd=5 ssthresh=5
[OK] same ssthresh, very different cwnd -> timeout cwnd=1 vs fast-retransmit cwnd=5
```

各行の `[OK]` は、「その操作の結果が予想通りだった」という意味です。特に最後の3行に注目してください。`CongestionState(cwnd=10, ssthresh=20)` という同じ出発点から、`on_timeout()` は `ssthresh=5` へ、`on_fast_retransmit()` も同じ `ssthresh=5` へ ―― **`ssthresh` の値は完全に一致する**のに、`cwnd` はタイムアウト側が1、ファスト再送側が5とまったく違う場所に着地しています。予想を立ててから走らせると、「同じ計算式でも呼び出す関数によって結果が変わる」という、この章でいちばん誤解されやすい点が体に入ります。

## この章を終えたと言える条件

ノートを見ずに、次を全部言えれば合格です。

- 「`phase()` は1つの比較であり、毎回計算し直される。どこにもキャッシュされたフェーズは無い」
- 「スロースタートはACK1つにつき1MSS足すだけ。輻輳回避はcwnd個分のACKがまるごと揃って初めて1MSS足す。後者は明示的なカウンタで数えていて、割り算はしていない」
- 「タイムアウトとファスト再送は同じ `ssthresh` を計算するが、タイムアウトは `cwnd` を1まで落とし、ファスト再送は新しい `ssthresh` にとどめる」

輻輳制御を「賢いアルゴリズム」として覚える必要はありません。読むべきは、1個の比較と、2個の加算規則と、2個の関数が共有する1つの計算式だけです。

次章では、届いた順番が入れ替わっても**データは失われていない**という主張を読みます。先に届いてしまった後続セグメントをどう扱うか、そしてギャップが埋まった瞬間に受信側が一気に追いつく仕組み ―― `reassembly.py` を開きます。
