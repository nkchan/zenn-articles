## この章の問い

シーケンス番号は32ビット、つまり `2**32` 通りの値しか持てません。接続が十分長く続けば、いつか必ず一周して0に戻ります。そのとき「aはbより前か」という問いに、普通の `<` はもう答えられません。ではTCPは、何を使って「前」を判定しているのか。

この章を読み終えると、次のことが言えるようになります。

- `SEQ_SPACE` が何を表す定数で、なぜ `2**32 - 1` ではなく `2**32` なのかを説明できる
- `seq_lt()` の「符号つき差分」トリックがどう動くか、そしてそれが「半周をどちらの意味とみなすか」という取り決めの上にしか成立しない理由を説明できる
- 平凡な `<` と `seq_lt()` が食い違う、具体的な数値の組を挙げられる
- `in_receive_window()` が何をチェックしているか、そしてなぜ `rcv_nxt` と `window` の両方が要るのかを説明できる

対応するソースファイルは `src/protocol_in_code/tcp/seqnum.py` です。

## この章にデータクラスが無い理由

第1章の `Segment`、第2章の `ConnectionState` ―― ここまでずっとデータクラスを読んできました。ところが `seqnum.py` にはデータクラスが1つもありません。すべての関数がただの整数を受け取り、整数を返します。

これは省略ではなく、この章の主題そのものです。ここで扱っているのは「検査すべき構造」ではなく、「リングの上での算術」です。構造体が要らないくらい、扱う対象がシンプルであること自体が、この章が伝えたいことの一部です。

まず、その算術がすべて従う法（modulus）を見ます。

```python
SEQ_SPACE = 2**32
```

`Segment.seq` は32ビットのフィールドでした（第1章）。取りうる値は `0` から `2**32 - 1` までの、ちょうど `2**32` 通り。だから `SEQ_SPACE` は `2**32` であって `2**32 - 1` ではありません ―― これは「最大値」ではなく「値の個数」、つまりこのリングの一周の長さです。以降のすべての関数は、この数を法にして計算します。

## `seq_add()` ―― 一周する、を具体的に見る

```python
def seq_add(a: int, n: int) -> int:
    """Sequence numbers live on a ring: adding past the top wraps back to zero."""
    return (a + n) % SEQ_SPACE
```

この章で最も単純な関数です。`SEQ_SPACE - 1` を超えて足すと、答えは0付近に戻ってくる。ただそれだけですが、これが「シーケンス番号はリングに住んでいる」という比喩を、抽象論ではなく実際に手で触れる形にしてくれます。後続の関数を読むときの土台はここにあります。

## `seq_lt()` ―― この章の本命

```python
def seq_lt(a: int, b: int) -> bool:
    """Is a 'before' b on the ring? The signed-difference trick: half the ring is 'ahead'."""
    return (b - a) % SEQ_SPACE < SEQ_SPACE // 2 and a != b
```

ここが読みどころです。`seq_lt(a, b)` は「aの数値がbより小さい」ではありません。「**aから前向きに歩いていくと、リングを半周する前にbに着く**」という意味です。

`(b - a) % SEQ_SPACE` は、aからbまで前向きに進んだときの距離を計算します。それが `SEQ_SPACE // 2` 未満、つまりリングの「近い半分」に収まっていれば、bはaの前方＝aより後にある、と判定します。

`and a != b` の一文は飾りではありません。`a == b` のとき `(b - a) % SEQ_SPACE` は `0` になり、これは間違いなく `SEQ_SPACE // 2` 未満です。このガードが無ければ、`seq_lt(a, a)` は `True` を返してしまい、「aはaより前」という矛盾した答えを返すことになります。このガードがあるからこそ、「ある値が自分自身より前になることはない」という保証が**偶然ではなく確実に**成り立ちます。

### 半分のリングが「前方」であるという取り決め

`seq_lt()` が成立するのは、リングをちょうど半分に切って、「近い半分にいるほうを前方とみなす」という取り決めがあるからです。この取り決めは、実際の2つのシーケンス番号の真の距離が `SEQ_SPACE // 2` に近い、あるいはそれを超えていたら意味を失います。この章のコードはその制約を強制しません ―― ウィンドウサイズをシーケンス空間の半分よりずっと小さく保つのは、呼び出す側の責任です。これは第4章で読む `window.py` が、なぜ小さい値しか扱わないのかにもつながります。

これが、TCPを本全体で貫くテーマ「符号なし比較の罠」の核心です。素朴な `<` は32ビット整数としての大小を見るだけで、リングという構造を知りません。だから境界をまたぐ比較では**必ず**間違えます。`seq_lt()` は同じ2つの数を見ても、リング上の前後関係という別の問いに答えている ―― 同じ入力に対して正反対の答えを返しうる、というのがこの章で一番効いてくる事実です。

## `seq_le()` ―― 独自の算術を持たない

```python
def seq_le(a: int, b: int) -> bool:
    return a == b or seq_lt(a, b)
```

`seq_le()` は自分でリング算術をやりません。等号チェックと `seq_lt()` の組み合わせだけでできています。「以下」は「前」に「等しい」を足しただけ、という最小の関係で組み立てられている ―― この章のもう一つの小さな観察です。

## `in_receive_window()` ―― 範囲チェックを距離チェックに変える

```python
def in_receive_window(seq: int, rcv_nxt: int, window: int) -> bool:
    """A seq is acceptable if it falls in [rcv_nxt, rcv_nxt + window), wrap included."""
    if window <= 0:
        return seq == rcv_nxt
    offset = (seq - rcv_nxt) % SEQ_SPACE
    return offset < window
```

2つの分岐しかありません。

`window <= 0` のとき、受理できる範囲は `rcv_nxt` というただ1点に潰れます。これは第4章の `advertised_window()` が生み出しうる「ゼロウィンドウ」のケースです。この分岐が先に判定を終わらせるため、後段の `offset` 計算まで落ちてくることはありません。

それ以外のとき、`offset = (seq - rcv_nxt) % SEQ_SPACE` が、`[rcv_nxt, rcv_nxt + window)` という**一周をまたぎうる範囲チェック**を、ただの `offset < window` という単純な比較に変換します。範囲の上限・下限を直接比べるのではなく、「`rcv_nxt` からどれだけ離れているか」という距離の問題に還元している ―― ここでも、比較を「値そのもの」ではなく「リング上の距離」で考える、この章の視点が繰り返されています。

## 自分で答える問い

ソースファイルを見て答えてください（docstring ではなく関数の本体で）。

1. `a = 2**32 - 1`、`b = 0` のとき、`seq_lt(a, b)` は何を返すか。同じ2つの値に対して素朴な整数の `<` は何を返すか。なぜ食い違うのか。
2. なぜ `seq_lt(a, a)` はどんな `a` に対しても `False` を返すのか。式のどの部分が、それを「たまたま」ではなく「保証」にしているか。
3. `seq == rcv_nxt + window` ちょうどのとき（1少ないのではなく）、`in_receive_window()` は `True` と `False` のどちらを返すか。`offset < window` の比較を辿って確かめよ。
4. `window == 0` のとき、`in_receive_window()` が受理する `seq` はただ1つ、どの値か。それを決めているのはどちらの分岐で、なぜ `offset` の計算まで落ちてこないのか。
5. `seq_lt(a, b)` が `False` かつ `a != b` のとき、`seq_le(a, b)` が `True` になることはあるか。`seq_le()` の定義を読んで根拠を示せ。

（問い1の答えの入口: `(b - a) % SEQ_SPACE = (0 - 4294967295) % 2**32 = 1`。これは `SEQ_SPACE // 2` 未満なので `seq_lt(a, b)` は `True`。一方、素朴な `<` は `4294967295 < 0` を評価するので `False`。同じ2つの数を見て、正反対の答えが出る。）

## 動かして確認する

```bash
PYTHONPATH=src python3 examples/tcp/session_03_walkthrough.py
```

walkthrough は、リングの天井から10手前の値を1つ作り、そこに20を足して一周させます。そのうえで、素朴な `<` が間違え `seq_lt()` が正しく答えるケースを示し、同じ考え方を `seq_le()` と、一周をまたぐ受信ウィンドウにまで広げます。実際に実行した出力は次の通りです。

```text
Session 03 walkthrough: Sequence numbers wrap around

[OK] seq_add wraps past 2**32    -> 4294967286 + 20 = 10
[OK] plain '<' wrong across wrap  -> plain says False, seq_lt says True
[OK] plain '<' and seq_lt agree   -> seq_lt(100, 200) = True
[OK] a seq is never lt itself     -> seq_lt(500, 500) = False
[OK] but it is le itself          -> seq_le(500, 500) = True
[OK] seq_le follows the wrap too  -> seq_le(4294967286, 10) = True
[OK] receive window spans the wrap -> seq 3 (past 0) accepted
[OK] just past the window is out   -> offset 25 >= window 20
[OK] zero window accepts only rcv_nxt -> True
```

各行の `[OK]` は「予想通りの結果になった」という意味です。特に2行目に注目してください ―― `4294967286` と `10` という同じ2つの数について、素朴な `<` は `False`、`seq_lt()` は `True` を返しています。**同じ入力、正反対の答え**。これが「符号なし比較の罠」の実物です。境界（0付近）をまたぐ比較でだけ、この食い違いが起きます。100と200のような、境界から遠い平凡な比較では両者は一致します（3行目）。この「境界近くでだけ壊れる」という性質こそが、この種のバグが本番環境で見つかりにくい理由です。

## この章を終えたと言える条件

ノートを見ずに、次を全部言えれば合格です。

- 「シーケンス番号は `2**32` の大きさのリングに住んでいる。『前』とは数値の大小ではなく、半周未満の前方距離のことだ」
- 「素朴な `<` が間違えるのは、比較が一周の境界をまたぐときだけ ―― `2**32` から `0` へのその一点の付近で、`seq_lt()` だけが正しい」
- 「受信ウィンドウは `rcv_nxt` から始まる範囲で、その範囲自体が一周をまたぎうる。だから `in_receive_window()` は絶対値の範囲ではなく、オフセット（距離）で判定している」

この章もまた、本書を貫くテーマの一つを体現していました ―― 「その数字は保存でなく計算」。`seq_lt()` も `in_receive_window()` も、どこかに答えを持っているわけではなく、渡された整数から**その場で**リング上の距離を計算し、答えを導いています。

次章では、この受信ウィンドウの「広さ」そのものを読みます。ウィンドウとは、相手にまだ残っている部屋の広さのこと ―― そしてこの数字もまた、保存されているのではなく、そのつど計算されるものです。`window.py` を開きます。
