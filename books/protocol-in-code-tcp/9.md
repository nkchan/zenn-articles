## この章の問い

セグメントが、受信側の期待より**先に**届いたとき、実際には何が起きているのか。そして、抜けていたセグメントがようやく届いた瞬間、なぜ**その1回の呼び出しだけ**で、待たされていた分すべてが一気に届くのか。

この章を読み終えると、次のことが言えるようになります。

- `deliver()` が返す3つの結果と、それを分ける比較がどれかを言える
- 順序が乱れて届いたセグメントが、なぜ `rcv_nxt` を一切動かさないのかを説明できる
- たった1回の `deliver()` 呼び出しが、渡されたバイト数よりはるかに多くを返せる理由を、コードを辿って示せる
- 「重複（既に届いた分）」と「長さゼロのセグメント」が、なぜ同じ結果になるのかを説明できる

対応するソースファイルは `src/protocol_in_code/tcp/reassembly.py` です。

## 順序が乱れる、とはどういう状態か

TCPはバイトストリームを提供しますが、下を流れるIPは順序を保証しません。セグメントAの直後に送ったセグメントBが、Aより先に届くことは普通に起こります。

ここで大事なのは、「順序が乱れる」ことと「失われる」ことはコード上まったく別の扱いだという点です。第6章で見た高速再送は、まさにこの区別に依存していました ―― 順序の入れ替わりを損失と誤認しないために、重複ACKが3回続くまで待つ。この章で読む `reassembly.py` は、その区別の**受信側の顔**です。先着したセグメントを捨てずに、ちゃんと居場所を与えて保持する仕組みを持っています。

## 2つの型 ―― 結果と保管場所

まず、この章で読む型そのものを見ます。

```python
class DeliveryOutcome(str, Enum):
    DELIVERED = "Delivered"
    BUFFERED = "Buffered"
    DUPLICATE = "Duplicate"


@dataclass(frozen=True)
class DeliveryResult:
    outcome: DeliveryOutcome
    delivered_len: int
    new_rcv_nxt: int


@dataclass
class ReassemblyBuffer:
    rcv_nxt: int
    segments: dict[int, int] = field(default_factory=dict)
```

`DeliveryResult` は `frozen=True` ―― 一度返した結果を、あとから書き換えることはできません。`delivered_len` と `new_rcv_nxt` が意味を持つのは `outcome is DELIVERED` のときだけですが、他の2つの結果でもこの2つのフィールドは必ず埋まっています（`0` と、変化していない `rcv_nxt`）。`None` にはしない。これが効くのは呼び出し側です ―― 「結果によっては値が無いかもしれない」という特別扱いを、呼び出し側は一切しなくて済みます。

`ReassemblyBuffer` はさらに小さく、2つのフィールドしかありません。

| フィールド | 意味 |
|---|---|
| `rcv_nxt` | 受信側が「順番通りに」次に期待しているシーケンス番号。「どこまで届いたか」を指す**唯一**のポインタ |
| `segments` | `seq -> payload_len` の辞書。`rcv_nxt` とまだ地続きになっていないセグメントが、ここに一時的に置かれる |

`segments` が保存しているのは**長さだけ**で、実際のバイト列ではありません。第1章で `payload_len` が「バイトをどう動かすか」ではなく「長さが何を意味するか」だけを表す整数だったのと同じ設計判断です。このおもちゃは一貫して、バイトの中身ではなく**帳簿**だけを扱っています。

## `deliver()` ―― 3方向の分岐

この章の本命です。

```python
def deliver(buffer: ReassemblyBuffer, seq: int, payload_len: int) -> DeliveryResult:
    """Out of order is not lost: it waits in the buffer until the missing bytes fill the gap."""
    if payload_len <= 0 or seq_lt(seq, buffer.rcv_nxt):
        return DeliveryResult(DeliveryOutcome.DUPLICATE, 0, buffer.rcv_nxt)

    if seq != buffer.rcv_nxt:
        buffer.segments[seq] = payload_len
        return DeliveryResult(DeliveryOutcome.BUFFERED, 0, buffer.rcv_nxt)

    # This segment lands exactly at rcv_nxt: drain every contiguous run that follows it.
    delivered_len = payload_len
    buffer.rcv_nxt = seq_add(buffer.rcv_nxt, payload_len)

    while buffer.rcv_nxt in buffer.segments:
        run_len = buffer.segments.pop(buffer.rcv_nxt)
        delivered_len += run_len
        buffer.rcv_nxt = seq_add(buffer.rcv_nxt, run_len)

    return DeliveryResult(DeliveryOutcome.DELIVERED, delivered_len, buffer.rcv_nxt)
```

分岐は上から順に3つ。判定は固定順序で走ります。

```text
payload_len <= 0 または seq が rcv_nxt より前  -> DUPLICATE （0バイト、rcv_nxt は不変）
seq != rcv_nxt（rcv_nxt との間にギャップがある） -> BUFFERED  （segments に保管、rcv_nxt は不変）
seq == rcv_nxt（ちょうど期待の縁に届いた）        -> DELIVERED （rcv_nxt が payload_len 分進み、
                                                                  さらに地続きになった分を
                                                                  1つずつ排出し続ける）
```

### 最初のチェック ―― `seq_lt()` を使う理由

1行目の `seq_lt(seq, buffer.rcv_nxt)` は、素朴な `<` ではなく、第3章で読んだシーケンス番号のリング比較を使っています。シーケンス番号は32ビットで一周する数字なので、単純な整数比較だと折り返しをまたいだときに「古いのに新しく見える」ケースが出ます。`seq_lt()` を経由することで、折り返しをまたいでいても、古いセグメントは確実に「古い」と判定されます。この章の `deliver()` は `seqnum.py` を単独で読むのではなく、**この最初の一行と合わせて**読む必要があります。

`payload_len <= 0` も同じ分岐にまとめられていることに注目してください。「もう届いている分の再送」と「そもそも運ぶものが無いセグメント」は、原因はまったく違いますが、`deliver()` にとってはどちらも「受信側の状態を一切変えない」という点で同じです。だから同じ `DUPLICATE` として1つのチェックにまとまっています。

### 真ん中のチェック ―― ギャップは「保管」であって「破棄」ではない

`seq != buffer.rcv_nxt` が真なら、そのセグメントは `rcv_nxt` より後ろにある ―― つまりまだ届いていないバイトの後に届いた、順序が乱れたセグメントです。ここでやることは1つだけ、`buffer.segments[seq] = payload_len` で辞書に置いておくこと。`rcv_nxt` はまったく動きません。

これがこの章の核心です。**先着したセグメントを捨てずに、`seq` をキーにして保持する**。失われてはいない ―― ただ、順番が来るまで座席で待っているだけです。

### 最後の分岐 ―― 縁に届いたら、そこで止まらない

`seq == buffer.rcv_nxt` のとき、そのセグメントは受信側がずっと待っていたバイトそのものです。`rcv_nxt` を `payload_len` 分進めるところまでは予想通りですが、そこで終わりません。`while buffer.rcv_nxt in buffer.segments:` というドレインループが続きます。

このループが読みどころです。`rcv_nxt` を進めるたびに、**その新しい `rcv_nxt` を鍵として** `buffer.segments` をもう一度引きます。もし以前バッファされたセグメントがちょうどそこにあれば、それも取り出して `delivered_len` に足し、`rcv_nxt` をさらに進める。これが「地続きである限り」続きます。

つまり、ギャップを埋めたのはこの呼び出しで渡された `payload_len` バイトだけなのに、**過去に貯めてあった分がまとめて雪崩式に排出される**。1回の `deliver()` 呼び出しの `delivered_len` が、その呼び出しに渡した `payload_len` を大きく超えることがある ―― それはバグではなく、この関数の設計そのものです。

## 自分で答える問い

ソースファイルを見て答えてください（docstring ではなく関数の本体で）。

1. `seq` が `buffer.rcv_nxt` とちょうど等しいセグメントが届いた。どの分岐が処理するか。ルーティングは `seq != buffer.rcv_nxt` を見て判定しているか、それとも `seq == buffer.rcv_nxt` を見ているか。
2. 3つのセグメントが順不同で届く ―― 最後のもの、次に真ん中のもの、最後にギャップを埋めるもの、という順で。この3回の `deliver()` 呼び出しのうち、何回が `DELIVERED` を返すか。その回の `delivered_len` はいくつか。
3. `payload_len = 0` のセグメントが `seq == buffer.rcv_nxt` の位置にちょうど届いた。これは `DELIVERED` になるか、`DUPLICATE` になるか。`seq` が `rcv_nxt` と比較される**前に**、どの行がこれを決めているか。
4. ギャップを埋める `deliver()` 呼び出しが一連のバッファ済みセグメントを排出したあと、その排出されたセグメントたちは `buffer.segments` からどうなっているか ―― 削除されるのか、それとも消費済みの印がつくだけか。
5. `buffer.segments` に既に入っている `seq` と同じ `seq` を持つセグメントが再度届いたら、その `seq` に対応する `payload_len` はどうなるか。`deliver()` のどの行がそれを決めているか。

（問い1の答えの入口: ルーティングを決めるのは `if seq != buffer.rcv_nxt:` という否定形の条件です。この式が偽になった、つまり `seq == buffer.rcv_nxt` だったときだけ、コードは条件を抜けてドレインループのある分岐に落ちます。）

## 動かして確認する

```bash
PYTHONPATH=src python3 examples/tcp/session_08_walkthrough.py
```

walkthroughは、順番通りのセグメントを1つ届け、次に順序が乱れた2つのセグメントをバッファし（両方とも `rcv_nxt` が動かないことを確認し）、最後にギャップを埋めるセグメントを送って、1回の `deliver()` 呼び出しが3セグメント分のバイトを一気に排出する様子を確かめます。さらに、古いセグメントと長さゼロのセグメントが両方とも `DUPLICATE` になることも確認します。実際の出力は次の通りです。

```text
Session 08 walkthrough: Out of order is not lost

[OK] in-order segment delivers      -> Delivered rcv_nxt=1100
[OK] out-of-order segment buffers   -> Buffered rcv_nxt unmoved=1100
[OK] second gap segment also waits  -> Buffered rcv_nxt unmoved=1100 pending=[1200, 1300]
[OK] gap-filler drains the whole run -> Delivered delivered_len=300 rcv_nxt=1400
[OK] stale segment is a duplicate   -> Duplicate rcv_nxt unchanged=1400
[OK] empty payload is not delivered -> Duplicate rcv_nxt unchanged=1400
```

4行目に注目してください。`deliver(buffer, 1100, 100)` という、渡した `payload_len` はたった100の呼び出しが、`delivered_len=300` を返しています。1100番のセグメント自身の100バイトに加えて、先に届いてバッファされていた1200番と1300番、合わせて200バイトが同じ呼び出しの中で排出されたということです。ドレインループが `while buffer.rcv_nxt in buffer.segments:` で辞書を引き直し続けた結果です。

各行の `[OK]` は、「その `deliver()` 呼び出しが予想通りの `outcome` と `rcv_nxt` になった」という意味です。予想と実際が食い違えば `[NG]` になります。まず、1300番と1200番が届いた時点で `buffer.segments` に何が入っているかを自分で書き出してから、1100番を渡したときに何が起きるかを予想して走らせると、ドレインループの動きが身体に入ります。

## この章を終えたと言える条件

ノートを見ずに、次を全部言えれば合格です。

- 「順序が乱れて届いたセグメントは、シーケンス番号をキーにバッファされる。`rcv_nxt` はギャップが閉じるまで動かない」
- 「ちょうど `rcv_nxt` に届いたセグメントは、それ自身を届けるだけでなく、その後ろに地続きになっている分をすべて、同じ1回の呼び出しの中で排出できる」
- 「`DUPLICATE` は『もう届いているデータ』と『そもそもバイトを持たないセグメント』の両方をカバーする。1つのチェックで両方を処理している」

そして、第6章の高速再送とこの章がどう呼応しているかも言えるようにしておいてください ―― 送信側は重複ACKを損失と誤認しないために3回待ち、受信側は順序が乱れたセグメントを損失と誤認せずに保管しておく。どちらも「順序の乱れ」と「本当の喪失」を区別するコードです。

次章では、この会話がどう**終わる**かを読みます。さよならは4パケットと待ち時間 ―― `teardown.py` を開き、なぜ終了にはちょうど4セグメントと、そのあとの待ち時間が必要なのかを追います。
