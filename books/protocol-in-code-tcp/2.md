## この章の問い

TCPセグメントは、実際には何を運んでいるのか。そして、**接続の状態を見るまでもなく**、フラグとペイロードの組み合わせだけで「これは意味を成さない」と分かるのはどんなときか。

この章を読み終えると、次のことが言えるようになります。

- `Segment` を構成する5つのフィールドを挙げられる
- なぜ `flags` が5つの真偽値やビットマスクではなく `frozenset[str]` なのかを説明できる
- `validate_segment()` がセグメントを拒否する全パターンと、その**判定順序**を言える
- なぜ「ペイロードを載せたRST」が、単に珍しいのではなく**不正**として扱われるのかを説明できる

対応するソースファイルは `src/protocol_in_code/tcp/segment.py` です。

## セグメントは5つのフィールド

まず、この章で読む型そのものを見ます。

```python
FLAG_NAMES = frozenset({"SYN", "ACK", "FIN", "RST"})


@dataclass(frozen=True)
class Segment:
    """A segment carries the conversation state: who is talking, and what they've heard."""

    seq: int
    ack: int
    flags: frozenset[str] = field(default_factory=frozenset)
    payload_len: int = 0
    window: int = 0
```

セグメントは、たった5つのフィールドです。

| フィールド | 意味 |
|---|---|
| `seq` | このセグメントが運ぶペイロード先頭バイトのシーケンス番号（ペイロードが無いなら制御フラグの位置） |
| `ack` | 送信側がここまで受け取った、という値。ACKフラグが立っているときだけ有効 |
| `flags` | 制御ビットの集合、例 `{"SYN", "ACK"}`。**5つの別々の真偽値ではなく集合**である |
| `payload_len` | 一緒に運ぶデータのバイト数。純粋な制御セグメントなら0 |
| `window` | このセグメントを送った時点で、送信側が広告している受信ウィンドウ |

### なぜ `flags` は集合なのか

ここが最初の読みどころです。`flags` は `is_syn` / `is_ack` / … という5つのブール値でも、ビットマスク用の整数でもなく、`frozenset[str]` です。

理由は、「**どのフラグが立っているか**」は**1つの事実**であって、5つの独立した事実ではないからです。集合なら「立っているフラグの一覧」がそのまま値になり、`"SYN" in flags` という自然な問いで答えられます。ビットマスクのようにビット演算でデコードする必要がありません。

そして `frozen=True` ―― 一度作ったセグメントは書き換えられません。これは第2章で効いてきます。ハンドシェイクではセグメントをあちこちに渡し、そのフィールドから返信を組み立てますが、「渡した先でセグメントが書き換わっているかも」と心配しなくて済むのは、不変だからです。

## フラグを読む4つの述語

`flags` に直接触る代わりに、このトラックの他のモジュールは全部この4つの述語を経由します。

```python
def is_syn(segment: Segment) -> bool:
    return "SYN" in segment.flags


def is_ack(segment: Segment) -> bool:
    return "ACK" in segment.flags


def is_fin(segment: Segment) -> bool:
    return "FIN" in segment.flags


def is_rst(segment: Segment) -> bool:
    return "RST" in segment.flags
```

1行ずつ、ただの集合メンバーシップ判定です。コメントも要らないほど小さい。小さいことに意味があります ―― `segment.flags` を直接触るコードが散らばると、フラグの表現を変えたくなったときに全箇所を直す羽目になる。述語1つに閉じ込めておけば、変更はここだけで済みます。

## 順序を与える `flags_label()`

```python
def flags_label(segment: Segment) -> str:
    """A human-readable rendering like 'SYN,ACK', in the conventional wire order."""
    order = ("SYN", "ACK", "FIN", "RST")
    present = [name for name in order if name in segment.flags]
    return ",".join(present) if present else "(none)"
```

`frozenset` には**それ自身の順序がありません**。`{"ACK", "SYN"}` と `{"SYN", "ACK"}` は同じ集合で、反復順は保証されない。人間に見せるときは慣習的なワイヤ順（SYN, ACK, FIN, RST）で並べたい ―― その順序を**与えているのがこの関数**です。順序はデータ側にあるのではなく、表示するこの場所で初めて生まれる。ここを押さえておくと、「順序はどこで決まるのか」という問いに毎回正しく答えられます。

## 検証 ―― 状態を見る前に決まる正しさ

この章の本命が `validate_segment()` です。

```python
class SegmentValidity(str, Enum):
    BAD_FLAG_NAME = "BadFlagName"
    SYN_FIN_TOGETHER = "SynFinTogether"
    PAYLOAD_WITHOUT_SEQ_MEANING = "PayloadWithoutSeqMeaning"
    NEGATIVE_LENGTH = "NegativeLength"
    VALID = "Valid"


def validate_segment(segment: Segment) -> SegmentValidity:
    """A segment's flags and payload must agree about what it means before anyone acts on it."""
    if not segment.flags <= FLAG_NAMES:
        return SegmentValidity.BAD_FLAG_NAME
    if is_syn(segment) and is_fin(segment):
        return SegmentValidity.SYN_FIN_TOGETHER
    if segment.payload_len < 0:
        return SegmentValidity.NEGATIVE_LENGTH
    if segment.payload_len > 0 and is_rst(segment):
        # A reset carries no data of its own; a payload on an RST has no seq meaning.
        return SegmentValidity.PAYLOAD_WITHOUT_SEQ_MEANING
    return SegmentValidity.VALID
```

4つの早期リターン。判定は**固定された順序**で走ります。

```text
flags が FLAG_NAMES の部分集合でない   -> BadFlagName
SYN と FIN が両方立っている            -> SynFinTogether
payload_len < 0                        -> NegativeLength
payload_len > 0 かつ RST が立っている  -> PayloadWithoutSeqMeaning
どれにも当たらない                     -> Valid
```

### この章で一番大事な観察

`validate_segment()` は、**一度も `ConnectionState` を見ていません**。ここでチェックしているのは全部、**セグメント単体の事実**です。「SYNとFINが同時に立っている」のは、接続がどの状態にあろうと常に間違い。「RSTがペイロードを運んでいる」のは、リセットには自分のデータのシーケンス上の意味が無いから常に間違い。

一方で、「この状態でこのセグメントを受け取っていいか」という**状態依存の正しさ**は、この章の問題ではありません。それは第2章 ―― ハンドシェイク ―― の仕事です。この境界線（**セグメント単体の正しさ / 状態に依存する正しさ**）をここで引けることが、この章の核心です。

判定順にも意味があります。未知のフラグは SYN+FIN チェックより**先に**弾かれ、負の長さは RST-ペイロードチェックより**先に**弾かれる。「まず名前が正しいか、次に組み合わせ、次に長さ」という素直な順序です。

## おもちゃの境界

実物のTCPセグメントは、チェックサム、データオフセット、オプション（MSS、ウィンドウスケーリング、SACK、タイムスタンプ）、URGフラグに紐づくurgentポインタを運びます。このおもちゃは、コースの残りが実際に推論に使う5フィールド（`seq`, `ack`, `flags`, `payload_len`, `window`）だけを残しました。

`FLAG_NAMES` があえて `{SYN, ACK, FIN, RST}` だけなのも同じ理由 ―― URG も PSH も ECE/CWR も無い。この4つが、第2章の状態遷移を全部駆動するフラグだからです。

そして `payload_len` は整数の**カウント**であって、実際のバイト列ではありません。このおもちゃは本物のペイロードバッファを一度も作りません。ここで読み取りたいのは「長さが何を意味するか」であって「バイトをどう動かすか」ではないからです。

## 自分で答える問い

ソースファイルを見て答えてください（docstring ではなく関数の本体で）。

1. `flags=frozenset({"SYN", "FIN", "URG"})` のセグメントは、どの `SegmentValidity` が返るか。なぜそのチェックが SYN+FIN チェックに**勝つ**のか。
2. なぜ `payload_len < 0` は、RSTに `payload_len > 0` が載っているのとは**別の**判定結果なのか。同じチェックにまとめない理由は。
3. `flags=frozenset()` かつ `payload_len=0` のセグメントは有効か。`validate_segment()` を辿って確認せよ。
4. `ack` に値があるのに ACK フラグが立っていないセグメントを、`validate_segment()` は拒否するか。docstring ではなく本体を読んで確かめよ。
5. なぜ `payload_len=0` の RST は検証を通り、同じ RST でも `payload_len=1` だと落ちるのか。

（問い1の答えの入口: `URG` は `FLAG_NAMES` の要素ではない。だから最初のチェックで `flags <= FLAG_NAMES` が偽になり、SYN+FIN を見るより前に `BadFlagName` で返る。）

## 動かして確認する

```bash
PYTHONPATH=src python3 examples/tcp/session_01_walkthrough.py
```

walkthrough は、正しい制御セグメント1つ、正しいデータセグメント1つ、そして `validate_segment()` が拒否する4通りそれぞれのセグメントを作り、最後に `flags_label()` がワイヤ順で描画することを確かめます。出力はこうなります。

```text
Session 01 walkthrough: A segment carries the conversation state

[OK] SYN, no payload            -> Valid
[OK] ACK carrying 50 bytes       -> Valid
[OK] unknown flag 'URG'          -> BadFlagName
[OK] SYN and FIN together        -> SynFinTogether
[OK] payload_len -1              -> NegativeLength
[OK] RST carrying a payload      -> PayloadWithoutSeqMeaning
[OK] flags_label on ACK segment  -> 'ACK'
[OK] flags_label keeps wire order -> 'SYN,FIN'
```

各行の `[OK]` は、「そのセグメントが**予想通りの判定結果になった**」という意味です。予想と実際が食い違えば `[NG]` になります。まず自分で結果を予想してから走らせると、`validate_segment()` の判定順が身体に入ります。

## この章を終えたと言える条件

ノートを見ずに、次を全部言えれば合格です。

- 「セグメントは5フィールド ―― `flags` は名前の集合であって、デコードすべきビットマスクではない」
- 「正しさは状態より先に決まる。SYN+FIN の同時は、接続がどの状態でも常に間違い」
- 「ペイロードを載せた RST が拒否されるのは、リセットには自分が運ぶと主張するデータのシーケンス上の意味が無いから」

次章では、この正しいセグメントたちが**状態を切り替える**様子を読みます。ハローに、なぜちょうど3つのパケットが要るのか ―― `handshake.py` を開きます。
