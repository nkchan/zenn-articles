## この章の問い

TCPの受信ウィンドウとは、実際には何なのか。そしてなぜそれは**保存される数字**ではなく、**毎回計算される数字**でしかありえないのか。

この章を読み終えると、次のことが言えるようになります。

- `advertised_window()` が使っている式と、その2つの入力を言える
- `ReceiveBuffer` になぜ `window` という独自フィールドが無いのかを説明できる
- 3つの `AcceptOutcome` を区別し、それぞれが起きる場面を挙げられる
- 「ウィンドウが再び開く」とは、具体的にどのフィールドが変化することなのかを説明できる

対応するソースファイルは `src/protocol_in_code/tcp/window.py` です。

## ウィンドウは「フィールド」ではなく「問いへの答え」

前章まででシーケンス番号という「どこまで話したか」を扱う道具を読みました。この章で扱うのは、その逆側 ―― 「相手はあとどれだけ話していいか」です。TCPを勉強すると「ウィンドウサイズ」という言葉がすぐに出てきて、まるでどこかの変数に `window = 60` と書いてあるような気がしてきます。しかし、このモジュールを読むと分かります。**そんな変数はどこにも無い**のです。

まず、この章が扱う型を見ます。

```python
@dataclass
class ReceiveBuffer:
    capacity: int
    buffered: int = 0
```

たった2つのフィールドです。

| フィールド | 意味 |
|---|---|
| `capacity` | 受信バッファの総容量。このおもちゃでは、バッファの生存期間中ずっと固定 |
| `buffered` | 今この瞬間、アプリケーションにまだ読まれずにバッファに溜まっているバイト数。**変化するのはこれだけ** |

`window` というフィールドは無い。これは書き忘れではありません。ウィンドウは `advertised_window()` という**関数**であって、`capacity - buffered` を尋ねられるたびに計算し直す値です。どこにもキャッシュされません。

前章の第1章で見た `Segment` は `frozen=True` でした。会話の1コマを表すセグメントは、一度作られたら変わらないほうが都合が良かった。今回の `ReceiveBuffer` は逆で、`@dataclass` のまま ―― つまり書き換え可能です。「今バッファにどれだけ溜まっているか」は、そのバッファの生存期間を通じて変わり続ける**状態**そのものだからです。不変にする理由がここには無い。

## `advertised_window()` ―― 1行の関数

```python
def advertised_window(buffer: ReceiveBuffer) -> int:
    """The window is how much room you have: capacity minus what's already sitting there."""
    return max(0, buffer.capacity - buffer.buffered)
```

これがこの章の核心です。ウィンドウは `capacity - buffered`。それ以上でもそれ以下でもありません。

`max(0, ...)` が付いているのには理由があります。もし何らかの理由でバッファが `capacity` を超えて溜まってしまった場合（このおもちゃの `accept()` は超過を許しませんが、防御的に）、`capacity - buffered` は負になり得ます。ウィンドウの広告値が負というのは意味を成しません ―― 「相手にマイナスのバイト数だけ送っていい」という広告はあり得ない。だから `0` で底を打たせています。

ここで、本書を貫くテーマがはっきり姿を見せます。**その数字は保存されていない、計算されている**。`ReceiveBuffer` のどこにも「今のウィンドウ」という値は存在しません。存在するのは `buffered` という1つの整数だけで、「ウィンドウ」はそれを毎回問い直した答えにすぎません。

## `accept()` ―― データが入るかどうかを決める

```python
def accept(buffer: ReceiveBuffer, payload_len: int) -> AcceptOutcome:
    """Data only enters the buffer if the advertised window actually had room for it."""
    room = advertised_window(buffer)

    if room <= 0:
        return AcceptOutcome.REFUSED

    if payload_len <= room:
        buffer.buffered += payload_len
        return AcceptOutcome.ACCEPTED

    # The sender overshot the last-known window; take what fits and drop the rest.
    buffer.buffered += room
    return AcceptOutcome.TRIMMED
```

`AcceptOutcome` は3種類です。

```python
class AcceptOutcome(str, Enum):
    ACCEPTED = "Accepted"
    TRIMMED = "Trimmed"
    REFUSED = "Refused"
```

読む順序に意味があります。まず `room = advertised_window(buffer)` で**その瞬間の**空き容量を一度だけ計算し、その `room` を以降の2つの分岐で使い回します。

- `room <= 0` なら、そもそも空きが無いので `REFUSED`
- `payload_len <= room` なら、全部収まるので `buffered` に `payload_len` をそのまま足して `ACCEPTED`
- どちらでもなければ、送信側が最後に知っていたウィンドウを超えて送ってきたということ。入るだけ（`room` バイトぶん）だけ `buffered` に足し、残りは捨てて `TRIMMED`

3つの分岐のうち、`buffered` に**足す量**と`payload_len`（送られてきた量）が食い違うのは `TRIMMED` だけです。ここが `accept()` を読むときに一番見落としやすいポイントで、「何バイト受け入れたか」を知りたければ `payload_len` ではなく、実際に `buffer.buffered` に加算された量を見る必要があります。

## `application_read()` ―― ウィンドウを開ける唯一の手段

```python
def application_read(buffer: ReceiveBuffer, n: int) -> int:
    """The application draining bytes is what reopens the window - never a separate knob."""
    freed = min(n, buffer.buffered)
    buffer.buffered -= freed
    return freed
```

`buffered` を増やせるのは `accept()` だけで、減らせるのは `application_read()` だけです。つまり「ウィンドウが再び開く」という現象は、`window` という値を誰かがどこかで書き換えることではなく、**`buffered` が減った結果、次に `advertised_window()` を呼んだときの答えが変わる**というだけのことです。

`freed = min(n, buffer.buffered)` にも注目してください。アプリケーションが実際に溜まっている量より多く読もうとしても、それはエラーにはなりません。ただ「実際にあった分」で頭打ちになり、本当に解放できたバイト数を返すだけです。ここでも「ちょうどぴったりの量を要求しないとエラーになる」という厳密さより、「持っている分だけ渡す」という素直な計算が選ばれています。

## この章で一番大事な観察

`window.py` を最初から最後まで読んでも、`buffer.buffered` を「今のウィンドウ計算結果」で直接上書きしているコードは一箇所も出てきません。`accept()` は `buffered` に足し算をし、`application_read()` は `buffered` から引き算をする ―― それだけです。ウィンドウという値そのものを代入している行は存在しません。

これはこのモジュールの設計の要です。もし `window` という独立したフィールドがあったら、`buffered` を更新するたびに `window` も同期して更新する処理が必要になり、更新を1箇所でも忘れれば「実際の空きバッファ量」と「相手に広告しているウィンドウ」がずれるバグが生まれます。フィールドを1つ減らし、代わりに「尋ねられたら計算する」関数にしてしまえば、ズレるということ自体が原理的に起こり得ません。**保存された値は、更新を忘れるとズレる。計算された値は、ズレようがない。**

## おもちゃの境界

実物のTCP受信ウィンドウは、ウィンドウスケーリング（RFC 9293 Section 3.8）、シリーウィンドウ症候群の回避、そして「開いたウィンドウを**いつ**相手に知らせるか」を決める遅延ACKのタイミング制御と絡み合っています。このおもちゃにはそのどれもありません。`accept()` と `application_read()` は、1つのバッファに対する同期的でローカルな操作にすぎず、通知すべき相手も、更新後のウィンドウ値を運ぶワイヤ上のセグメントも登場しません。

`accept()` の `TRIMMED` という結果も単純化です。行儀の良い送信側は、そもそも広告されたウィンドウを超えてデータを送ってくることはないので、実物の受信側が「ウィンドウを超えた分だけ黙って受け入れて残りを捨てる」という挙動をすることは通常ありません。このおもちゃがあえて `TRIMMED` を防御的な分岐として残しているのは、`room` と `payload_len` の大小比較という算術そのものを読ませたいからで、送信側の規約違反への対処を教えたいからではありません。

そして `ReceiveBuffer.capacity` は、このモジュールの中では一度も変化しません。実物のバッファサイズの自動調整（オートチューニング）やメモリ圧迫時の縮退は、このおもちゃの範囲外です。

## 自分で答える問い

ソースファイルを見て答えてください（docstring ではなく関数の本体で）。

1. `capacity=100, buffered=100` のバッファがある。`advertised_window()` は何を返すか。そして次に `accept(buffer, 1)` を呼ぶと、`accept()` のどの分岐が処理するか。
2. `accept()` の `TRIMMED` 分岐で、`buffer.buffered` は実際には何バイト増えるか ―― `payload_len` か、それとも別の値か。その値を決めている行を引用せよ。
3. `application_read(buffer, n)` を、`n` が `buffer.buffered` より大きい値で呼んだとき、戻り値は何か。`buffer.buffered` は負になり得るか。
4. このファイルの中に、`buffer.buffered` を計算済みのウィンドウ値へ直接セットしているコードパスはあるか。その不在は、「ウィンドウ」が実際にはどこに存在しているかについて何を教えてくれるか。
5. `buffered == capacity` のちょうどそのとき、`max()` が適用される**一歩手前**で `advertised_window()` の中の算術は `0` か、それとも負の値か。`max(0, ...)` の中身を先にトレースせよ。

（問い1の答えの入口: `advertised_window()` は `max(0, 100 - 100)` で `0` を返す。`accept()` はまず `room = advertised_window(buffer)` を計算するので `room = 0` となり、最初の `if room <= 0:` に該当して `REFUSED` になる。）

## 動かして確認する

```bash
PYTHONPATH=src python3 examples/tcp/session_04_walkthrough.py
```

walkthrough は、容量100バイトのバッファを作り、ウィンドウがゼロに縮んで拒否が起きるまでデータを受け入れ続け、そのあとで `application_read()` を呼び、**同じバッファ**が再びデータを受け入れられるようになる ―― それが `buffered` の減少だけによって起きたこと ―― を確かめます。出力はこうなります。

```text
Session 04 walkthrough: The window is how much room you have

[OK] empty buffer, full window   -> 100
[OK] accept 40 bytes             -> Accepted, window now 60
[OK] accept 50 more bytes        -> Accepted, window now 10
[OK] send 30, only 10 fits        -> Trimmed, window now 0
[OK] window is zero, refuse       -> Refused
[OK] application reads 25 bytes   -> freed 25, window now 25
[OK] window reopened, accept 20   -> Accepted, window now 5
[OK] read past buffered, capped   -> freed 95, window now 100
```

各行の `[OK]` は、そのステップの結果が**予想通りだった**という意味です。特に注目したいのは3行目と6行目です。3行目では30バイト送っても10バイトしか入らず `Trimmed` になり、ウィンドウはきっちり `0` に落ちます。6行目では `application_read()` を呼んだだけで、`accept()` を一度も呼んでいないのにウィンドウが `25` まで開きます。ウィンドウという値をどこかで直接セットしていないことの、動く証拠です。

## この章を終えたと言える条件

ノートを見ずに、次を全部言えれば合格です。

- 「ウィンドウは `capacity - buffered` であり、毎回その場で計算される値。どこにも保存されておらず、ズレて古くなることがない」
- 「`accept()` の結果は3通りで、`Trimmed` だけが『送られてきたバイト数』と『実際にバッファへ足された量』が一致しない分岐」
- 「ウィンドウが再び開くのは `application_read()` が `buffered` を減らすからで、それ以外にウィンドウを動かすレバーは存在しない」

次章では、時間そのものを扱います。再送タイマーは、一度決めた「正しい待ち時間」を使い続けるのではなく、RTTを観測するたびにその待ち時間を**学習し直します**。`rto.py` を開き、毎RTTごとに変わっていく「正しい待ち時間」の計算を読みます。
